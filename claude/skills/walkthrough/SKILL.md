# Walkthrough

방금 생성된 코드를 **사람이 검토할 수 있도록** 안내하는 문서를 만든다. 코드를 쓴 에이전트가 저자(author), 사용자가 리뷰어(reviewer)다.

존재 이유는 **코드에 남지 않는 정보** - 스펙에 없어 추측으로 채운 지점, 대안 중 하나를 고른 지점. 정적 리뷰로는 복원할 수 없고 코드를 생성한 에이전트만 안다.

## 경계

- **결함·버그 탐지는 하지 않는다.** 그건 `/code-review`, `/simplify` 몫. 같은 diff를 두 번 훑어 결론이 엇갈리면 리뷰어만 혼란스럽다.
- 이 스킬은 *설명*한다. 판정이 필요한 것은 직접 판단하지 말고 `사람 판단 필요`로 넘긴다.
- **호출 시점**: 대화 컨텍스트가 살아 있는 동안. 세션이 끝나거나 컨텍스트가 압축된 뒤에는 `사람 판단 필요`를 채울 수 없다.
- **확인 질문은 리뷰어가 따라가며 배우는 용도.** 중요한 부분을 요약 읽기로 끝내지 않고 코드로 한 홉씩 확인하게 한다. 질문 본문의 `볼 곳` 링크로 시도하고, 막히면 접힌 `힌트` → `답` 순서로 펼친다 - 답을 펼쳐 읽는 것도 정상 경로라 답 자체를 학습 자료로 쓴다.
  - `code-tour`와 달리 검증 모드가 없다. 질문 근거가 세션 기억이라 나중에 재도출할 수 없고, 문서 `**** 답`이 유일한 정본이다 - 대조는 사용자가 펼쳐서 한다.
  - 커밋과 독립된 동작·테스트 이해 확인은 `/code-tour <범위>` 몫. 여기는 이 문서의 세션 결정·요약을 코드로 확인하는 질문만 낸다.
  - 상태 전환(`TODO` → `DONE`)은 사용자 몫. 스킬은 `TODO`로 만들기만 한다.

## 프로세스

### 1. 범위 결정

**처음 맞는 것**을 쓴다.

1. 인자로 지정된 범위(커밋 범위 / 경로 / PR 번호)
2. 대화 컨텍스트에 있는 이번 세션의 커밋·변경 합집합 ← 기본 브랜치에 직접 커밋하는 워크플로의 실질적 기본값
3. uncommitted(staged + working tree)
4. `merge-base..HEAD` (현재 브랜치 ≠ 기본 브랜치)
5. 전부 실패 → **추측하지 말고 사용자에게 확인**

컨텍스트 없이 콜드로 호출됐으면 `사람 판단 필요`에 *"세션 컨텍스트 없음 - 추론 불가"*라고 명시한다. 임의로 채우지 않는다.

### 2. 탐색

- `CONTEXT.org`(다중 컨텍스트면 `CONTEXT-MAP.org` → 각 `CONTEXT.org`)가 있으면 읽어 그 용어를 문서 전반에 쓴다. **읽기만** 한다 - 갱신은 `domain-modeling` 몫.
- 건드리는 영역에 `docs/adr/` ADR이 있으면 찾아 둔다.
- 둘 다 없으면 넘어간다(강제하지 않음).
- 독자 프로필: [reader-profile.md](../shared/reader-profile.md)로 변경 범위의 언어·버전·프레임워크를 판정하고, 빠진 프로필은 물어 기록한 뒤 **낯선 영역**을 정한다.

### 3. 변경 분석

Skill 도구로 `explain-change`를 **인라인 호출**한다(세션 컨텍스트 유지).

- 넘기는 것: §1에서 정한 범위 그대로 - 커밋 범위면 hash/범위, uncommitted면 diff 텍스트, 저장소 위치도 함께.
- 요청할 다이어그램: `auto` - 트리거에 해당하는 것만([diagrams.md](../shared/diagrams.md)).
- §2에서 정한 낯선 영역(없으면 생략).

분담:

- **코어**: diff·코드베이스로 알 수 있는 것만, 위치·형태의 **사실 서술로**(`codebase-design` 어휘 참조, 평가·판정 없음).
- **이 스킬**: 코어가 못 내는 것을 세션 컨텍스트로 보강 - `basis: inferred` → `사람 판단 필요`, 사전 지식의 "왜 이걸 골랐나·대안", 그 밖에 세션에서만 아는 "왜".

### 4. 문서 작성

`~/walkthrough/YYYY-MM-DD-HHMM-<slug>.org`에 쓴다(`<slug>` = 변경 주제 kebab). 디렉터리가 없으면 만든다.

| 문서 섹션 | 재료 |
| --- | --- |
| 헤드라인 | `stat`(범위·규모) |
| 아키텍처 델타 | `units[].architecture` + `impact`(호출자가 새로 알아야 할 참조처) - 축당 1줄로 압축 |
| 아키텍처 다이어그램 | `diagrams` |
| 사전 지식 | `prerequisites` + 세션이 아는 "왜·대안" |
| 읽는 순서 | `reading_order` |
| 워크스루 | `units[].summary`(설명) + `evidence`(근거 코드) |
| 사람 판단 필요 | `basis: inferred` + 세션 컨텍스트(결정 주체, 열린 지점, 대안) |
| 확인 질문 | `아키텍처 델타` 요지 축 + `사람 판단 필요` 항목 + `워크스루` 논리 단위 + `사전 지식` 개념 + `evidence` 위치 |
| 다루지 않은 변경 | `omitted` |

코어 결과의 경로는 맨 경로 - 문서에 옮길 때 org 링크로 바꾼다([code-locations.md](../shared/code-locations.md)).

### 5. 포매팅

먼저 [code-locations.md](../shared/code-locations.md)의 검사를 생성한 .org 파일에 실행하고, 출력이 없을 때까지 위반을 고친다.

이어서 문서 안 heading 링크(`[[*<제목>]`)가 실제 heading을 가리키는지 검사한다. 출력이 있으면 대상 없는 링크 - 제목을 맞추고 다시 실행한다.

```bash
f=<생성한 .org 파일>
awk 'FNR==NR { if (match($0, /^\*+ /)) { h = substr($0, RLENGTH + 1); sub(/^(TODO|KEEP|REVERT|DONE) /, "", h); gsub(/ *\[[0-9]*(%|\/[0-9]*)\]/, "", h); sub(/[ \t]+(:[^ \t]+:)?[ \t]*$/, "", h); H[h] = 1 } next } { s = $0; while (match(s, /\[\[\*[^]]+\]/)) { t = substr(s, RSTART + 3, RLENGTH - 4); if (!(t in H)) print FILENAME ":" FNR ": " t; s = substr(s, RSTART + RLENGTH) } }' "$f" "$f"
```

그다음 [org-formatting.md](../shared/org-formatting.md)의 정렬을 실행한다.

### 6. 보고

채팅에는 문서 전문을 쏟지 말고 아래만 출력한다.

- 이번 변경의 정체 한 줄
- 아키텍처 델타 핵심 1~2줄
- `사람 판단 필요` 건수 - 결정 주체별(에이전트 단독 / 무응답 진행 / 사용자 답)
- `확인 질문` 체인 개수, 질문 개수
- 생성한 org 파일의 **절대 경로**

## 작성 규칙

### 선별

- **논리 단위별로 묶는다. 파일별이 아니다.** 파일 경계는 아키텍처 경계와 일치하지 않는다.
- **완전성보다 선별.** 총량 상한은 없지만 리뷰어가 봐야 할 것만 싣는다.
- **생략한 것은 `다루지 않은 변경`에 반드시 적는다.** 선별 요약은 *"이게 전부인가?"*에 답하지 못하면 신뢰받지 못한다. 포매팅, 기계적 반복, 자동 생성 파일 등을 한 줄로 묶어 명시한다.
- **발췌는 최소 라인만.** hunk·함수 통째 복붙 금지. 논리 단위당 20줄 이내, 설명의 근거가 되는 줄만, 원본 인덴트 유지. 언어가 불명확하면 `#+begin_example`.
- **기존 코드를 고친 evidence는 diff로 전/후를 보여준다.** `evidence.before`가 있으면 `#+begin_src diff`(`-`/`+` + 원본 인덴트), 없으면(순수 신규 추가) 지금처럼 `#+begin_src <lang>`. diff도 최소 대비 라인만 - git 원본 hunk를 그대로 복붙하지 않는다. `before`+`snippet` 합산으로 논리 단위당 20줄 상한은 동일.
- **빈 섹션은 "없음"으로 명시한다.** 통째로 지우면 "해당 없음"과 "확인 안 함"이 구분되지 않는다. 예외는 `사전 지식`과 `아키텍처 델타 > ADR` 둘뿐.

### 아키텍처 델타

**요약이지 나열이 아니다.** 리뷰어가 3초 안에 구조 변화를 잡는 게 목적 - `units[].architecture`를 그대로 펼치면 실패한다.

- **요지 1줄 + 델타 5줄 상한.** 넘으면 뺀다. 세부는 워크스루 본문에 근거 코드와 함께 나오므로 잃는 정보가 없다.
- **`요지`는 델타 전체를 한 줄로.** 나머지를 안 읽어도 구조 변화를 잡을 수 있게 쓴다.
- **모든 줄이 `<축>: <전> → <후>`.** 신설·삭제도 `없음 → =AssetValidator=` / `=LegacyParser= → 없음`. 전후 대비가 안 잡히면 델타가 아니므로 워크스루로 내린다.
- **축당 1줄.** 한 축에 여러 건이면 대표 하나만 쓰고 `외 N곳`으로 뭉친다. 예: =WatchWorkoutDisplay= → =WatchWorkoutSelection= , 시그니처 4곳 전파.
- **축은 이번 변경에서 실제 움직인 것만.** 모듈·인터페이스·의존성·소유권·흐름은 흔한 예일 뿐 고정 목록이 아니다. 안 움직인 축은 줄째로 뺀다. 축이 전부 비면 섹션에 "없음" 한 줄.
- **경로는 다음 줄에 단독으로.** 축당 대표 위치 1개만. 줄 끝에 붙이면 줄이 길어져 정작 스캔할 앞부분이 밀린다.
- **ADR은 하위 섹션으로 분리한다.** 델타 줄과 섞으면 `전 → 후` 스캔이 끊긴다.

### 사람 판단 필요

문서에서 가장 중요한 섹션이다. 목표는 리뷰어가 **세션 기록 없이** 항목마다 승인(`KEEP`) 또는 뒤집기(`REVERT`)를 판정하고, 그 결과를 후속 작업으로 추적하는 것.

- **섹션 heading에 통계 쿠키 `[/]`**를 붙여 접힌 채로 남은 판정 수를 보이게 한다.
- **항목 = `** TODO` heading 하나.** 스킬은 `TODO`로만 만든다. `KEEP`/`REVERT` 전환은 사용자 몫 - 사용자 답 항목도 `TODO`로 둔다(리뷰 시점 재확인).
- **결정 주체**는 셋 중 하나: `에이전트 단독`(아무도 확인 안 함), `질문 후 무응답 진행`(물었으나 명시 답 없음), `사용자 답`(사용자가 고름).
- **항목 순서**: 결정 주체(에이전트 단독 > 무응답 진행 > 사용자 답) -> 같은 그룹 안에서 뒤집기 비용 큰 순. 리뷰어가 승인 책임을 많이 지는 것부터.
- **`**` 본문은 짧은 속성 bullet만**(`결정 주체`, `위치`). 하위 내용이 붙는 필드는 전부 `***` heading + heading 요약으로 올린다 - 접힌 개요만 읽어도 결정 이야기가 통하고, bullet 나열이 쌓이지 않는다.
- **`***` 순서 고정**: 열린 지점 -> 선택 -> 선택 코드 -> 선택 흐름 -> 대안 -> 대안 흐름 -> 뒤집기 비용.
  - `열린 지점`: 왜 판단이 필요했나. spec/티켓/ADR에서 비어 있거나 모호한 곳을 인용하거나 "언급 없음"으로.
  - `선택`: 이유 bullet 1단, bullet 하나에 이유 하나.
  - `대안`: `택했다면` - 코드/동작에서 달라지는 것. 대안이 여럿이면 `*** 대안 1 - ...` / `*** 대안 1 흐름 - ...` 짝으로.
  - `선택 코드`, `선택 흐름`, `대안 흐름`은 재료가 없으면 heading째 생략("없음"을 쓰지 않는다). 나머지는 필수.
  - 더 쪼갤 내용이 있으면 `****` heading을 써도 된다 - bullet 깊이를 늘리는 대신 heading으로 올린다.
- **세션 은어 금지.** "티켓 06", "선택 3번", "spec 문구" 같은 세션 내부 참조는 그 내용을 풀어 쓰거나 원문을 인용한다. 리뷰어는 세션을 보지 않았다.
- **`뒤집기 비용`은 사실만**: 바뀌는 파일, 설정 포맷, 계약, 테스트. 크다/작다 평가는 하지 않는다(판정 회피).
- **코드 발췌**: `선택 코드`에 선택이 강제되는 최소 라인. 항목당 20줄 상한(선별 규칙과 동일).
- **다이어그램** - 내용이 [diagrams.md](../shared/diagrams.md) 카탈로그 kind의 질문에 답하면 쓴다.
  - 선택 vs 대안: 차이가 분기 판정이면 `logic`, 호출 순서면 `sequence`, 설정/데이터 모양이면 `er`. 같은 kind로 선택 1장 + 대안 1장, 차이 노드만 `:::highlight`.
  - `열린 지점`, `뒤집기 비용` 등 다른 `***` heading도 내용이 kind 질문에 맞으면 쓴다.
  - heading 하나에 블록 하나([org-writing.md](../shared/org-writing.md) 코드 블록 규칙).
  - `:file` = `~/walkthrough/<slug>-decision-<n>-<part>.png`(`<n>` = 항목 순번, `<part>` = `open` | `chosen` | `alt[-k]` | `cost`).
  - 선택/대안 대비는 이 스킬 고유 패턴이다. 표기 규칙은 diagrams.md를 따른다.

### 확인 질문

중요한 부분을 요약 읽기로 끝내지 않고 코드로 따라가며 확인해 배우게 한다. 리뷰어는 시간이 부족하다 - 질문 하나를 링크 하나 따라가 1-2분에 답할 크기로 줄이고, 여러 홉 경로는 질문 여러 개의 **체인**으로 쪼갠다. 답을 펼쳐 읽어도 배우도록 답을 풍부하게 쓴다.

- **체인 = 재료 항목 하나**(`**` heading). 재료
  - `아키텍처 델타` - `요지`에 해당하는 축 하나만. 델타가 "없음"이면 없음
  - `사람 판단 필요` 항목 - `사용자 답` 항목은 제외(사용자가 직접 고른 결정이라 `KEEP`/`REVERT`로 충분)
  - `워크스루` 논리 단위 - 요약이 코드 경로를 압축한 곳
  - `사전 지식` 개념 - `reader-unfamiliar`이고 `등장 위치`가 이번 변경 코드에 있는 것
  - 테스트 기반 질문(테스트가 고정한 규칙과 그걸 지키는 코드)은 내지 않는다 - 결함·테스트 판정 쪽이라 `/code-review`·`/code-tour` 몫.
- **수**: 문서당 체인 최대 5개. 아래 우선순위대로 채우고 5개가 차면 멈춘다 - 중요도 판단만으로는 전부 중요하다고 채우게 되므로 숫자로 막는다. 재료 항목당 체인 최대 1개. 재료가 없으면 섹션에 "없음" 한 줄 - 억지로 내지 않는다.
  1. 아키텍처 델타 (최대 1개)
  2. 사람 판단 필요 (그 섹션 순서)
  3. 워크스루 (읽는 순서)
  4. 사전 지식
- **체인 순서**: 위 우선순위와 같다. 체인끼리 독립 - 어디서 멈춰도 앞 체인은 완결된다.
- **질문 안 낸 재료**: 재료인데 체인을 안 낸 항목을 섹션 본문 맨 위 `- 질문 안 낸 재료` 아래에 heading 링크 + 사유로 적는다. 사유는 `상한` / `확정 불가` / `사용자 답` / `before 없음` 중 하나 - *"이게 전부인가?"*에 답하기 위해.
- 콜드 호출이면 `사람 판단 필요` 체인은 없다(추론 불가).
- **홉**: 체인당 2-3개(`*** TODO <n>. <질문>`, 번호 = 따라갈 순서). 아키텍처 델타는 3개 고정. 넘으면 체인을 쪼개지 말고 핵심 구간만 남긴다 - 쪼개면 체인 상한을 우회한다.
  - 1홉 = `볼 곳` 링크 하나 안에서 답이 나오는 크기. 파일을 건너가야 하면 홉을 나눈다.
  - 앞 홉의 답이 다음 홉의 출발점이 되게 잇는다.
- **아키텍처 델타 체인 홉 모양**: [codebase-design](../codebase-design/SKILL.md) 어휘로 고정. 위치 찾기("새 클래스 어디 있나")로 끝나지 않게 한다.
  1. 인터페이스 - 호출자가 이제 알아야 하는 것(시그니처, 불변식, 에러 모드)
  2. 숨긴 것 - 전에 호출자가 하던 일 중 구현 안으로 들어간 것. before 코드(diff `-` 쪽)가 근거
  3. 마지막 홉 - 아래 고정 규칙
  - before/after 대비가 없거나 확정할 수 없으면 체인째 버린다(`before 없음` / `확정 불가`).
- **마지막 홉은 재료별로 고정**
  - 아키텍처 델타: 델타 모양으로 분기
    + 신설/추출 모듈: 삭제 테스트 - "=X=를 지우면 복잡성이 어느 호출부에서 되살아나나" - before 호출부가 답
    + 그 외(인터페이스 축소, 소유권 이동, 흐름 변경 등): 지역성 반사실 - "<변경 시나리오>면 전에는 몇 곳, 지금은 어디를 고치나". 시나리오는 세션에서 논의된 것 우선, 없으면 델타 축에서 도출
  - 사람 판단 필요: 대안 반사실 - "대안 X였다면 이 경로의 몇 번 홉이 어떻게 바뀌나"
  - 사전 지식: 주의점 추적 - "주의점 W가 이 경로의 어느 홉에서 걸리나"
  - 워크스루: 추적 홉만(고정 홉 없음)
- **체인 `**` 본문**: `출처`(재료 heading 링크) / `배경`(출처 핵심 1-3 bullet 발췌) / `출발점`(첫 코드 위치). heading 요약은 `<N>홉, <재료 종류>`. 상태 키워드 없음.
- **질문 `***` 본문**: `볼 곳` 링크 하나만, 펼친 채로 둔다 - 1홉이라 링크 공개가 답 공개가 아니고, 접으면 따라가기가 느려진다.
- `**** 힌트` / `**** 답`(이 순서, 상태 키워드 없음, 둘 다 필수). 서브heading이라 문서를 열면 접혀 있다.
  - **힌트**: `볼 곳` 안에서 무엇을 찾을지 - 심볼/조건 지목. 정답 문장은 쓰지 않는다.
  - **답**: 결론 한두 문장 + `위치` 링크 + 근거 최소 라인 발췌 + `다음 홉`(마지막 홉은 생략). 발췌는 홉당 10줄 안팎.
- **`*** 정리`**: 체인 마지막. 다이어그램 1장 + 홉별 링크 목록(`홉 <n>: <링크> - <일어나는 일>`) + 반사실/주의점 홉이면 대안 경로 한 줄.
  - 다이어그램은 홉 번호를 노드/메시지에 붙인다(`1. Compile`) - 결정 다이어그램(선택 vs 대안)과 달리 "밟은 순서"에 답한다.
  - kind: 홉이 함수 경계를 넘으면 `sequence`, 한 함수 안이면 `logic`, 설정/데이터 모양 추적이면 `er`. 표기는 [diagrams.md](../shared/diagrams.md).
  - `:file` = `~/walkthrough/<slug>-quiz-<체인 순번>.png`.
  - 1홉 질문 안에는 다이어그램을 넣지 않는다 - 코드 몇 줄이 더 빠르다.
- **문서 안 참조는 순번 금지**("사람 판단 필요 3번째" X). `[[*<heading 제목>][<라벨>]]` 링크를 걸고, 필요한 내용은 그 자리에 발췌한다 - 문서 위아래로 오가게 하지 않는다.
  - 제목은 TODO 키워드/태그를 뺀 heading 텍스트와 완전 일치(org가 키워드를 매칭에서 제외 - 사용자가 `KEEP`/`REVERT`로 바꿔도 유지).
- heading 하나에 물음 하나, 한 문장. 묶으면 heading이 문단이 된다 - 홉으로 나눈다.
- **확정 가능한 것만.** 출제 시점에 정답을 스스로 확정한다 - 확정 못 하면 그 홉은 버린다. 의견·취향을 묻지 않는다.
- 상태: 질문 `*** TODO` -> 사용자가 `DONE`. 스킬은 `TODO`로만 만든다.
- **진행 표시**: 접힌 상태에서 남은 질문이 보이게 통계 쿠키를 단다.
  - 체인 `**` heading 끝에 `[/]` - 직속 `*** TODO` 질문을 센다.
  - `* TODO 확인 질문` 끝에 `[/]` + `:COOKIE_DATA: todo recursive` drawer - 체인(TODO 키워드 없음)을 건너 질문 전체를 센다.
  - 스킬은 빈 `[/]`만 쓴다. 개수는 §5 정렬(`org-update-statistics-cookies`)이 채우고, 이후엔 emacs가 상태 전환마다 갱신한다.
  - heading 링크 매칭에서 org는 쿠키를 무시한다 - 링크 제목에 쿠키를 넣지 않는다.

### 판정 회피

- **사전 지식 판정 기준은 "이 코드베이스에 선례가 없는 것" + "독자 프로필상 낯선 것" 둘뿐이다.** 앞은 `grep`으로, 뒤는 기록된 프로필로 확인한다 - 사용자가 알지 모를지 그 밖의 근거로 추측하지 않는다.
  - 대상: 라이브러리·프레임워크, 언어 기능, 설계 패턴, 알고리즘, 프로토콜·포맷
  - 제외: 이미 코드베이스에 널린 관용구, 일반 상식 - 단 독자 프로필상 낯선 영역에 속하면 포함
- **ADR과 어긋나면 판정하지 말고 넘긴다.** 준수하면 `아키텍처 델타 > ADR`에 `ADR-<NNN> 준수`로 서술, 어긋나면 결함으로 규정하는 대신 `사람 판단 필요` 항목으로 만든다 - `열린 지점`에 ADR-<NNN> 해당 문구를 인용하고, `선택`에 다르게 구현한 근거를 적는다.

### org 표기

- **코드 위치는 [code-locations.md](../shared/code-locations.md)의 org 규칙을 따른다** - 어디에 쓰든 `[[file:/abs/path/foo.ts::42][foo.ts:42]]`, 같은 파일 반복도 전체 target, 링크는 verbatim 금지. 채팅 보고의 경로는 맨 경로.
- **본문은 [org-writing.md](../shared/org-writing.md)를 따른다** - 짧은 문장 plain list, 깊이별 기호 교대, 출처 위치, 코드 블록 배치, 공통 표기.
- **식별자는 verbatim `=...=`로 감싼다**(예: =FLHitWindowRunner=). 안에 `=` 문자를 넣지 않는다(구문이 깨진다) - 대입식은 평문으로.
- **다이어그램은 `diagrams`를 그대로 org mermaid 블록으로 싣는다.**
  - `:file`은 `~/walkthrough/<slug>-<kind>.png`(`<kind>` = 그 항목의 kind), `sequence`는 `-<시점 slug>`를 붙여 장마다 고유하게. 크기 옵션은 블록에 쓰지 않는다(ob-mermaid 기본값).
  - 표기·렌더 공통 규칙은 [diagrams.md](../shared/diagrams.md).
  - mermaid 소스는 편집·재작성 금지(verbatim `=` 규칙과 무관).
  - 렌더는 온디맨드 - 사용자가 `C-c C-c`/export로 PNG를 만든다(pre-render하지 않는다).
