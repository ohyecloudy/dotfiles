# Walkthrough

방금 생성된 코드를 **사람이 검토할 수 있도록** 안내하는 문서를 만든다. 코드를 쓴 에이전트가 저자(author), 사용자가 리뷰어(reviewer)다.

존재 이유는 **코드에 남지 않는 정보** - 스펙에 없어 추측으로 채운 지점, 대안 중 하나를 고른 지점. 정적 리뷰로는 복원할 수 없고 코드를 생성한 에이전트만 안다.

## 경계

- **결함·버그 탐지는 하지 않는다.** 그건 `/code-review`, `/simplify` 몫. 같은 diff를 두 번 훑어 결론이 엇갈리면 리뷰어만 혼란스럽다.
- 이 스킬은 *설명*한다. 판정이 필요한 것은 직접 판단하지 말고 `사람 판단 필요`로 넘긴다.
- **호출 시점**: 대화 컨텍스트가 살아 있는 동안. 세션이 끝나거나 컨텍스트가 압축된 뒤에는 `사람 판단 필요`를 채울 수 없다.

## 프로세스

### 1. 범위 결정

**처음 맞는 것**을 쓴다.

1. 인자로 지정된 범위(커밋 범위 / 경로 / PR 번호)
2. 대화 컨텍스트에 있는 이번 세션의 커밋·변경 합집합 ← 기본 브랜치에 직접 커밋하는 워크플로의 실질적 기본값
3. uncommitted(staged + working tree)
4. `merge-base..HEAD` (현재 브랜치 ≠ 기본 브랜치)
5. 전부 실패 → **추측하지 말고 사용자에게 확인**

컨텍스트 없이 콜드로 호출됐으면 `사람 판단 필요`에 *"세션 컨텍스트 없음 - 추론 불가"*라고 명시한다. 임의로 채우지 않는다.

### 2. 탐색

- `CONTEXT.org`(다중 컨텍스트면 `CONTEXT-MAP.org` → 각 `CONTEXT.org`)가 있으면 읽어 그 용어를 문서 전반에 쓴다. **읽기만** 한다 - 갱신은 `domain-modeling` 몫.
- 건드리는 영역에 `docs/adr/` ADR이 있으면 찾아 둔다.
- 둘 다 없으면 넘어간다(강제하지 않음).

### 3. 변경 분석

Skill 도구로 `explain-change`를 **인라인 호출**한다(세션 컨텍스트 유지).

- 넘기는 것: §1에서 정한 범위 그대로 - 커밋 범위면 hash/범위, uncommitted면 diff 텍스트, 저장소 위치도 함께.
- 요청할 다이어그램: `module`·`class`·`sequence` **3종 전부**.

분담:

- **코어**: diff·코드베이스로 알 수 있는 것만, 위치·형태의 **사실 서술로**(`codebase-design` 어휘 참조, 평가·판정 없음).
- **이 스킬**: 코어가 못 내는 것을 세션 컨텍스트로 보강 - `basis: inferred` → `사람 판단 필요`, 사전 지식의 "왜 이걸 골랐나·대안", 그 밖에 세션에서만 아는 "왜".

### 4. 문서 작성

`~/walkthrough/YYYY-MM-DD-HHMM-<slug>.org`에 쓴다(`<slug>` = 변경 주제 kebab). 디렉터리가 없으면 만든다.

| 문서 섹션 | 재료 |
| --- | --- |
| 헤드라인 | `stat`(범위·규모) |
| 아키텍처 델타 | `units[].architecture` + `impact`(호출자가 새로 알아야 할 참조처) |
| 아키텍처 다이어그램 | `diagrams` |
| 사전 지식 | `prerequisites` + 세션이 아는 "왜·대안" |
| 읽는 순서 | `reading_order` |
| 워크스루 | `units[].summary`(설명) + `evidence`(근거 코드) |
| 사람 판단 필요 | `basis: inferred` + 세션 컨텍스트 |
| 다루지 않은 변경 | `omitted` |

```org
#+title: Walkthrough - <한 줄 제목>

* 헤드라인

  - <이번 변경의 정체 한 줄>
  - 범위: <SHA 범위 | uncommitted> - 파일 <N>개, +<A>/-<B>
  - 사전 지식: <목록 | 없음>
  - 사람 판단 필요: <N>건

* 아키텍처 델타

  - 요지: <이 변경의 구조적 정체 한 줄>
  - 모듈: <신설·삭제·이동한 모듈>
  - 인터페이스: <호출자가 새로 알아야 하는 것>
  - 의존성: <방향 변화>
  - 소유권: <상태·데이터 소유권 이동>
  - 흐름: <변경 후 데이터 흐름>
  - ADR-<NNN> 준수 - <어느 부분이>        ← 관련 ADR 있을 때만

* 아키텍처 다이어그램                       ← diagrams 없으면 "없음" 한 줄

** <title>

   - <caption 한 줄>
   #+begin_src mermaid :file ~/walkthrough/<slug>-<kind>.png :width "1200"
   <mermaid 소스>
   #+end_src

* 사전 지식(prerequisite)                  ← 해당 없으면 섹션 통째 생략

** <개념명>

   - 무엇: <한 줄>
   - 왜 여기 필요했나: <한 줄>
   - 대안: <한 줄>
   - 주의점: <한 줄>
   - 등장 위치: /abs/path/foo.ts:40

* 읽는 순서

  1. /abs/path/foo.ts:12 - <왜 여기부터>
  2. /abs/path/bar.ts:88 - <왜 그다음>

* 워크스루

** <논리 단위 제목>

   - <설명 한 줄>
   /abs/path/foo.ts:40
   #+begin_src ts
   <근거 라인만>
   #+end_src
   - <설명 한 줄>

* 사람 판단 필요

  - <결정> - 근거: <…>, 대안: <…> → /abs/path/foo.ts:40
                                              ← 없으면 "없음" 한 줄

* 다루지 않은 변경

  - <생략분과 이유>
```

### 5. 포매팅

쓴 뒤 emacs로 org 들여쓰기를 정렬한다(emacs에서 열었다 저장한 것과 같은 상태). 여러 파일을 한 번에 넘길 수 있다. emacs가 없거나 실패하면 파일은 그대로 두고 사용자에게 그 사실만 알린다.

```bash
emacs -Q --batch --eval '(progn (require (quote org)) (setq org-adapt-indentation t) (let ((dir default-directory)) (dolist (f command-line-args-left) (find-file (expand-file-name f dir)) (org-mode) (org-indent-region (point-min) (point-max)) (save-buffer))))' <생성한 .org 파일들>
```

### 6. 보고

채팅에는 문서 전문을 쏟지 말고 아래만 출력한다.

- 이번 변경의 정체 한 줄
- 아키텍처 델타 핵심 1~2줄
- `사람 판단 필요` 건수
- 생성한 org 파일의 **절대 경로**

## 작성 규칙

### 선별

- **논리 단위별로 묶는다. 파일별이 아니다.** 파일 경계는 아키텍처 경계와 일치하지 않는다.
- **완전성보다 선별.** 총량 상한은 없지만 리뷰어가 봐야 할 것만 싣는다.
- **생략한 것은 `다루지 않은 변경`에 반드시 적는다.** 선별 요약은 *"이게 전부인가?"*에 답하지 못하면 신뢰받지 못한다. 포매팅, 기계적 반복, 자동 생성 파일 등을 한 줄로 묶어 명시한다.
- **발췌는 최소 라인만.** hunk·함수 통째 복붙 금지. 논리 단위당 20줄 이내, 설명의 근거가 되는 줄만, 원본 인덴트 유지. 언어가 불명확하면 `#+begin_example`.
- **빈 섹션은 "없음"으로 명시한다.** 통째로 지우면 "해당 없음"과 "확인 안 함"이 구분되지 않는다. 예외는 `사전 지식` 하나뿐.

### 아키텍처 델타

- **축 라벨을 접두어로 고정한다.** `요지`·`모듈`·`인터페이스`·`의존성`·`소유권`·`흐름` 순서. 라벨이 없으면 렌더된 문서만 보고는 그 줄이 어느 축인지 알 수 없다.
- **`요지`는 델타 전체를 한 줄로.** 나머지를 안 읽어도 구조 변화를 잡을 수 있게 쓴다.
- **해당 없는 축은 줄을 생략한다.** 축이 전부 비면 섹션에 "없음" 한 줄.
- **한 축에 여러 건이면 같은 라벨로 줄을 반복한다.** `units[]`가 여럿이어도 단위별로 쪼개지 말고 축 순서를 유지해 묶는다.
- **변화는 `전 → 후`로 적는다.** 신설·삭제는 `신설`/`삭제`. 예: =Run()= 인자 2 → 3개 / =AssetValidator= 신설.

### 판정 회피

- **사전 지식 판정 기준은 "이 코드베이스에 선례가 없는 것"이다.** `grep`으로 확인 가능한 객관적 기준을 쓴다 - 사용자가 알지 모를지 추측하지 않는다.
  - 대상: 라이브러리·프레임워크, 언어 기능, 설계 패턴, 알고리즘, 프로토콜·포맷
  - 제외: 이미 코드베이스에 널린 관용구, 일반 상식
- **ADR과 어긋나면 판정하지 말고 넘긴다.** 준수하면 `아키텍처 델타`에 `ADR-<NNN> 준수`로 서술, 어긋나면 결함으로 규정하는 대신 `사람 판단 필요`에 *"ADR-<NNN>과 다르게 구현. 근거: …"*로 적는다.

### org 표기

- **코드 위치는 어디에 쓰든 `/abs/path/foo.ts:42`**(절대 경로 + 단일 라인). emacs `ffap`/compilation-mode 점프용.
  - 금지: 상대경로(`foo.ts:42`), 라인 범위(`:42-50`), verbatim으로 감싸기(점프가 막힌다).
  - 산문에 인라인해도 된다 - 형식만 맞으면 문장 중간에서도 점프된다.
- **한 항목 = 한 bullet = 물리적으로 한 줄.** 문장 중간 하드 줄바꿈 금지(길어도 한 줄, 표시는 emacs soft-wrap).
- **식별자는 verbatim `=...=`로 감싼다**(예: =FLHitWindowRunner=). 안에 `=` 문자를 넣지 않는다(구문이 깨진다) - 대입식은 평문으로.
- **verbatim 뒤에 한글 조사를 붙이지 않는다.** `=Foo=에`는 org가 마크업으로 인식하지 못해 export에서 깨진다. 조사가 안 붙게 문장을 쓰고, 부득이하면 한 칸 띄운다.
- **헤딩 아래 본문은 별 개수 + 1칸 들여쓴다**(`*` → 2칸, `**` → 3칸).
- **다이어그램은 `diagrams`를 그대로 org mermaid 블록으로 싣는다.**
  - `:file`은 `~/walkthrough/<slug>-<kind>.png`(`<kind>` = 그 항목의 kind), `:width "1200"`으로 폭 통일.
  - mermaid 소스는 편집·재작성 금지(verbatim `=` 규칙과 무관).
  - 렌더는 온디맨드 - 사용자가 `C-c C-c`/export로 PNG를 만든다(pre-render하지 않는다).
