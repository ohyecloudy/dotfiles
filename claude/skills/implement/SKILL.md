# Implement

사용자가 지정한 spec 또는 티켓에 기술된 작업을 구현한다.

가능한 곳에서는 사전 합의된 심(seam)에서 `/tdd`로 진행한다.

티켓에 `인수 기준(acceptance criteria)` 섹션이 있으면, 심 합의 때 기준별 검증 방법도 **함께** 분류해 사용자 확인을 받는다(확인 왕복 1회). 인수 기준이 없는 티켓·spec 단독이면 인수 기준 검증 관련 단계는 모두 건너뛴다.

- **테스트**: 자동 테스트로 덮인다 - 어느 심의 테스트인지 명시
- **`/run`**: 실제 앱을 구동해 확인
- **검증 불가**: 실기기·외부 서비스 필요, 주관적 판단 등 - 사용자 수동 검증 몫

블로커(Blocked by) 티켓이 `ready-for-human`이면 착수는 하되, 최종 보고에 "미검증 블로커 위에서 진행" 경고를 남긴다.

타입체크(typecheck)를 자주, 개별 테스트 파일을 자주 돌리고, 전체 테스트 스위트(test suite)는 마지막에 한 번 돌린다.

## 인수 기준 검증

전체 스위트 직후, `/code-review` 전에 한다. 합의된 방법으로 기준을 하나씩 검증한다.

- 통과 항목은 티켓에 **대문자** `- [X]`로 체크한다.
- 실패 항목은 `/tdd`로 수정한 뒤 재검증한다. **수정 재시도 상한: 1회** - 그 뒤에도 같은 항목이 실패하면 중단하고, 실패 항목과 원인을 보고한 뒤 사용자 판단을 기다린다.
- 검증 불가 항목은 `- [ ]`로 둔다.

모든 기준 검증이 끝나면 티켓 drawer의 `:STATUS:` 줄을 갱신한다(`:STATUS_ALL:`은 그대로, 어휘 정본은 [to-tickets](../to-tickets/SKILL.md)의 "티켓 status").

- 전부 `- [X]` → `done`
- 검증 불가 항목이 남음 → `ready-for-human`

## 검토와 커밋

완료되면 `/code-review`로 작업을 검토한다. 리뷰 반영으로 코드가 바뀌었으면, 그 변경이 영향을 주는 인수 기준만 커밋 전에 재검증한다.

작업을 현재 브랜치에 커밋한다. 커밋 메시지 작성 시 `/commit-message` 사용.

- in-repo 티켓이면 체크·status 변경을 구현 커밋에 포함한다.
- 외부 모드(`~/project-docs/...`) 티켓이면 파일만 갱신하고 커밋하지 않는다([project-docs-storage.md](../shared/project-docs-storage.md)).
- 코드 주석·커밋 메시지에 저장소 밖 문서(ADR·CONTEXT·spec·티켓)를 참조하지 않는다([저장소 텍스트의 문서 참조](../shared/project-docs-storage.md)).

## 보고

- 기준별 검증 근거(어떤 테스트 / `/run`으로 무엇을 확인)
- 사용자 수동 검증 필요 항목
- 미검증 블로커 경고(해당 시)

완료 후, 사람이 결과를 검토할 워크스루 문서가 필요하면 `/walkthrough`를 제안한다. 대화 컨텍스트가 살아 있을 때만 온전히 생성되므로 이 시점에 안내한다. 직접 실행하지는 않는다.
