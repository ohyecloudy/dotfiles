`/grilling` 세션을 진행한다. 목적은 `/poc`이 사용자 개입 없이 끝까지 달릴 수 있을 만큼 착수 조건을 굳히는 것이다.

## 수렴 목표

아래 4개 **합의 항목**이 모두 채워질 때까지 파고든다. 정본은 [poc](../poc/SKILL.md)의 "합의 항목".

- **검증할 질문**: 예/아니오 또는 수치로 답할 수 있는 형태로 다듬는다. "X가 괜찮은가?"(X) -> "X 방식으로 Y가 Z ms 안에 되는가?"(O)
- **완료 조건**: 관측 가능한 실행 증거로 표현한다. "잘 동작"(X) -> "N개 스폰 시 프레임 X ms 이하가 로그에 찍힘"(O)
- **비교할 대안**: 대안마다 `구현`(실제로 만들어 실측) 또는 `분석만`(코드·문서 근거로 비교)을 지정하고, 비교 축(성능, 메모리, 구현 복잡도 등)을 정한다. 결정적 차이가 실측으로만 드러나는 대안만 `구현`을 추천한다.
- **범위 밖**: PoC에서 다루지 않을 것.

## 대안 발굴

사용자가 대안 하나만 들고 오면 코드베이스와 일반 지식으로 다른 대안을 적극 제시한다. trade-off 정리의 재료가 여기서 나온다.

## PoC 불필요 판정

코드·문서 탐색만으로 답이 나오는 질문이면 PoC 대신 그 자리에서 근거와 함께 답하고 세션 종료를 제안한다.

## 산출물 경계

- **파일·코드를 쓰지 마라.** 착수 조건이 아무리 굳었어도 마찬가지다. 구현과 정리 문서는 `/poc` 몫이다.
- `CONTEXT.org`·ADR도 갱신하지 않는다. 버릴 수도 있는 실험으로 도메인 모델을 오염시키지 않는다.

## 세션 종료

4개 합의 항목을 대화에 정리하고 멈춘다. `/poc`은 대화 맥락을 그대로 읽어 착수하므로 별도 인계 문서를 만들 필요가 없다.

- 모두 확정 -> `/poc` 제안 한 줄. 예) "착수 조건이 굳었다. PoC를 시작하려면 `/poc`을 호출하라."
- 미확정 항목이 남음 -> 무엇이 남았는지만 밝히고 제안하지 않는다

제안한 스킬을 직접 실행하지 마라. 사용자가 다음 턴에 호출한다.
