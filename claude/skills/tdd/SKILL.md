# Test-Driven Development

TDD는 red → green 루프다. 이 스킬은 그 루프가 **간직할 가치가 있는 테스트**를 만들어내게 하는 레퍼런스다: 좋은 테스트란 무엇인가, 테스트는 어디에 두는가, 안티패턴(anti-pattern), 그리고 루프의 규칙. 모든 섹션은 매 사이클마다 적용된다 — 루프가 끝난 뒤가 아니라 루프 전·중에 참조한다.

코드베이스를 탐색할 때 `CONTEXT.md`(다중 컨텍스트면 `CONTEXT-MAP.md` → 각 `CONTEXT.md`)를 읽어 테스트 이름과 인터페이스 어휘를 프로젝트의 도메인 언어에 맞추고, 건드리는 영역의 ADR을 존중한다. tdd는 glossary를 *읽기만* 한다 — 새 용어 확정·갱신은 `domain-modeling` 몫.

## 좋은 테스트란

테스트는 구현 세부사항(implementation detail)이 아니라 **공개 인터페이스(public interface)를 통해 동작(behavior)을 검증**한다. 코드는 통째로 바뀔 수 있어도 테스트는 그대로여야 한다. 좋은 테스트는 명세(specification)처럼 읽힌다: "user can checkout with valid cart"는 어떤 기능이 존재하는지 정확히 알려주고, 내부 구조에 신경 쓰지 않으므로 리팩터링을 견뎌낸다.

예시는 [tests.md](tests.md), 모킹(mocking) 가이드라인은 [mocking.md](mocking.md) 참고.

## 심(seam): 테스트를 두는 곳

**심(seam)**은 테스트하는 공개 경계(public boundary)다: 내부에 손대지 않고 동작을 관찰하는 인터페이스. 테스트는 심에 존재하며, 내부(internals)를 상대로는 절대 두지 않는다.

**사전 합의된 심에서만 테스트하라.** 테스트를 쓰기 전에 테스트 대상 심을 적어 사용자에게 확인받는다. 합의되지 않은 심에는 테스트를 쓰지 않는다. 모든 것을 테스트할 수는 없으므로, 심을 미리 합의하는 것이 테스트 노력을 모든 엣지 케이스가 아니라 핵심 경로(critical path)와 복잡한 로직에 집중시키는 방법이다.

물어라: "공개 인터페이스는 무엇이고, 어떤 심을 테스트해야 하나?"

그 인터페이스의 형태 자체가 의문일 때(모듈이 얼마나 깊은지, 심을 어디에 둘지, 인터페이스가 무엇을 노출해야 할지) Skill 도구로 "codebase-design"을 호출해 어휘를 참조하라. 이는 모듈(module)·인터페이스(interface)·깊이(depth)·심(seam)·어댑터(adapter)·레버리지(leverage)·지역성(locality) 용어의 공유 출처이며, 실행할 세션이 아니라 참조할 레퍼런스다.

## 안티패턴

- **구현 결합(implementation-coupled)**: 내부 협력자(internal collaborator)를 모킹하거나, private 메서드를 테스트하거나, 사이드 채널로 검증한다(인터페이스 대신 데이터베이스를 직접 조회). 징후: 동작은 그대로인데 리팩터링하면 테스트가 깨진다.
- **동어반복(tautological)**: 단언(assertion)이 기대값을 코드와 똑같은 방식으로 재계산한다(`expect(add(a, b)).toBe(a + b)`, 손으로 같은 방식으로 만든 스냅샷, 상수를 자기 자신과 같다고 단언). 그래서 구성상 항상 통과하며 코드와 결코 어긋날 수 없다. 기대값은 독립적인 진실의 출처(source of truth)에서 와야 한다: 알려진 정답 리터럴(known-good literal), 손으로 푼 예제, 명세.
- **수평 슬라이싱(horizontal slicing)**: 모든 테스트를 먼저 쓴 다음 모든 구현을 쓴다. 대량 테스트는 _상상한_ 동작을 검증한다: 사용자 관점의 동작이 아니라 _형태_ 를 테스트하게 되고, 테스트가 실제 변경에 둔감해지며, 구현을 이해하기 전에 테스트 구조에 스스로를 묶는다. 대신 **수직 슬라이스(vertical slice)**로 작업하라: 테스트 하나 → 구현 하나 → 반복, 각 테스트는 지난 사이클이 가르쳐 준 것에 반응하는 **트레이서 불릿(tracer bullet)**이다.

## 루프의 규칙

- **Red before green.** 실패하는 테스트를 먼저 쓰고, 그 다음 통과시킬 만큼의 코드만 쓴다. 미래의 테스트를 예상하거나 추측성 기능을 추가하지 마라.
- **한 번에 한 슬라이스.** 한 사이클에 심 하나, 테스트 하나, 최소 구현 하나.
- **리팩터링은 루프의 일부가 아니다.** 리팩터링은 루프 밖 별도 정리 패스에 속한다(`simplify` 스킬 참고) — red → green 구현 사이클이 아니다.
