# PoC

일을 정의해 넘기기 **전에** "되는가, 어떤 trade-off인가"를 결과로 확인한다. 산출물은 둘이다.

- 동작하는 완성물 - 현재 작업 트리에 커밋된 코드
- 정리 문서 - 결론, trade-off, 검증 근거, 핵심 코드 학습. 본인 판단·학습용 독립 문서로, spec·티켓과 연계하지 않는다

속도가 우선이다. 코드 품질은 본 구현 몫이므로 TDD·`/code-review`는 하지 않는다. 대신 **결론마다 실행 증거**를 남긴다 - 증거 없는 결론은 정리 문서의 신뢰를 깎는다.

## 전제

- 대화 맥락에 `/grill-for-poc`으로 합의한 4개 합의 항목이 있어야 한다. 없거나 비었으면 `/grill-for-poc`을 먼저 하라고 안내하고 멈춘다. 빈칸을 추측으로 채우지 않는다.
- 착수 후에는 **비인터랙티브**로 진행한다. 합의는 grill에서 끝났다 - 종료 조건에 닿을 때까지 사용자를 붙잡지 않는다.
- git 저장소가 아니면 착수 전에 알리고 멈춘다(커밋 단위 기록이 시도 로그·학습 섹션의 전제).

## 합의 항목

합의 항목 어휘의 정본. `grill-for-poc`이 여기를 참조한다.

- 검증할 질문 - 예/아니오 또는 수치로 답할 수 있는 형태
- 완료 조건 - 관측 가능한 실행 증거
- 비교할 대안 - 대안별 `구현`/`분석만` 지정 + 비교 축
- 범위 밖

## 저장 위치 판정

먼저 저장소 루트를 보고 in-repo인지 외부(`~`)인지 결정한다. 전체 규칙은 [project-docs-storage.md](../shared/project-docs-storage.md) 참고. 정리 문서는 `docs/pocs/<slug>/poc.org`(`<slug>` = 검증할 질문 주제 kebab), 외부 모드면 `~/project-docs/<정규화 경로>/docs/pocs/<slug>/poc.org`.

## PoC status

PoC status 어휘의 정본. 파일 맨 위 property drawer의 `:STATUS:` 속성에 쓰고, 허용값은 같은 drawer의 `:STATUS_ALL:`에 공백으로 나열한다. status를 바꿀 때는 `:STATUS:` 줄만 고친다.

- `in-progress` - 착수 초기값
- `done` - 검증할 질문에 답이 나옴. 완료 조건 충족과 가설 반증("불가 + 근거") 모두 여기
- `blocked` - 막힘. 부분 결론 + 막힌 원인
- `needs-human` - 결론은 났으나 사람만 확인할 수 있는 실행 증거가 남음

## 프로세스

### 1. 착수

- `git rev-parse HEAD`로 **시작 커밋**을 기록한다. 학습 섹션 범위의 기준이다.
- 아래 템플릿으로 poc.org 골격을 만든다: drawer(`in-progress`, `:CREATED:`, `:BASE_COMMIT:`) + `* 합의` 섹션. 나머지 섹션은 heading만 둔다.
- 골격을 착수 직후 쓰는 이유: PoC가 길어져 컨텍스트가 압축돼도 합의 항목과 시도 로그가 파일에 남는다.

### 2. 구현

- 현재 작업 트리·현재 브랜치에서 한다. worktree·브랜치를 만들지 않는다.
- `구현` 지정 대안만 구현한다. `분석만` 대안은 코드·문서 근거로만 비교한다.
- **자주 커밋한다.** 동작하는 작은 단계마다, 그리고 대안 경계마다 커밋을 나눈다 - 나중에 대안별 비교·발췌가 쉬워진다. 커밋 메시지는 `/commit-message`로 쓴다.
- 스테이징은 PoC가 만든·고친 파일만 경로로 지정한다. 착수 전부터 있던 사용자의 미커밋 변경을 쓸어 담지 않는다.
- push 하지 않는다. push는 사용자 몫이다.
- 코드 주석·커밋 메시지에 저장소 밖 문서를 참조하지 않는다([저장소 텍스트의 문서 참조](../shared/project-docs-storage.md)).

### 3. 동작 확인

결론마다 실행 증거를 만든다: 빌드 성공 + 실행 명령과 출력 요약(수치면 수치 그대로). 증거는 `* 검증 근거`에 커밋 hash와 함께 적는다.

사람만 확인할 수 있는 증거(에디터 시각 확인, 실기기 등)는 `* 수동 확인 필요`에 확인 방법과 함께 남기고 진행한다.

### 4. 시도 로그 누적

접근을 버리거나 대안 하나를 끝낼 때마다 `* 시도 로그`에 한 줄 추가한다: 무엇을 시도 / 왜 버렸나(또는 결과) / 커밋 hash. 버린 접근의 "왜"는 코드에도 커밋에도 남지 않는 trade-off의 핵심 재료다 - 나중에 몰아 쓰지 말고 그때그때 쓴다.

### 5. 종료 조건

아래 중 하나에 닿으면 구현을 멈추고 6단계로 간다.

- 완료 조건 충족 -> `done`
- 가설 반증("안 된다"가 실행으로 증명됨) -> `done`. 결론에 "불가 + 근거"
- 같은 장애(빌드 실패, 가설과 다른 동작 등)에 **접근을 2번 바꿔도** 진전 없음 -> `blocked`. 그 지점까지의 부분 결론 + 막힌 원인
- 위 결론이 났지만 `* 수동 확인 필요` 항목이 남음 -> `needs-human`

### 6. 학습 섹션

- 독자 프로필: [reader-profile.md](../shared/reader-profile.md)로 PoC 코드의 언어·버전·프레임워크를 판정하고, 빠진 프로필은 물어 기록한 뒤 **낯선 영역**을 정한다. 비인터랙티브 원칙의 유일한 예외 - 이미 기록돼 있으면 묻지 않는다.
- Skill 도구로 `explain-change`를 **인라인 호출**한다(세션 컨텍스트 유지). 넘기는 것: 범위 `<시작 커밋>..HEAD`, 저장소 위치, 낯선 영역(없으면 생략), `evidence: full`. 다이어그램은 요청하지 않는다.
- 결과로 `* 사전 지식`, `* 핵심 코드 워크스루`를 채우고, 세션 컨텍스트로 "왜 이걸 골랐나·대안"을 보강한다. 코어 결과의 맨 경로는 org 링크로 바꾼다([code-locations.md](../shared/code-locations.md)).
- `* TODO 확인 질문`은 trade-off 결정 지점 위주로 2~4개. 막히면 `힌트 1` -> `힌트 2` -> `답` 순으로 펼친다.

### 7. 결론 작성

`* 결론`, `* trade-off`를 마지막에 채우고 `:STATUS:`를 갱신한다. trade-off 표의 각 셀에 근거가 `실측`인지 `분석`인지 표시한다 - 추측이 실측처럼 읽히지 않게.

### 8. 포매팅

먼저 [code-locations.md](../shared/code-locations.md)의 검사를 poc.org에 실행하고 출력이 없을 때까지 고친다. 그다음 [org-formatting.md](../shared/org-formatting.md)의 정렬을 실행한다.

### 9. 문서 커밋

- in-repo면 poc.org를 커밋한다(마지막 PoC 커밋에 포함하거나 별도 `docs:` 커밋).
- 외부 모드(`~/project-docs/...`)면 파일만 두고 커밋하지 않는다.

### 10. 보고

채팅에는 문서 전문을 쏟지 말고 아래만 출력한다.

- 검증할 질문에 대한 답 한 줄
- status
- `수동 확인 필요` 항목(있으면)
- 커밋 범위 `<시작 커밋>..HEAD`
- poc.org **절대 경로** (홈 아래면 `~`로 줄임, Windows는 `D:/...`처럼 슬래시)

## 템플릿

```org
:PROPERTIES:
:STATUS_ALL: in-progress done blocked needs-human
:STATUS:   in-progress
:CREATED:  [<YYYY-MM-DD> <영어 요일 약어: Mon..Sun>]
:BASE_COMMIT: <시작 커밋 hash>
:END:
#+title: PoC - <검증할 질문 요약>

* 결론

  - 답: <예 | 아니오 | 수치 | 조건부> - <한 줄>
  - 핵심 근거: <실측 결과 한 줄> - <커밋 hash>

* 합의

  - 검증할 질문: <...>
  - 완료 조건: <...>
  - 비교할 대안
    - <대안 A> - 구현
    - <대안 B> - 분석만
  - 비교 축: <성능, 메모리, 구현 복잡도 ...>
  - 범위 밖: <...>

* trade-off

  | 축     | 대안 A           | 대안 B           |
  |--------+------------------+------------------|
  | <축 1> | <값> (실측)      | <값> (분석)      |
  |--------+------------------+------------------|

* 검증 근거

  - <결론 항목> - <실행 명령> -> <출력 요약> - <커밋 hash>

* 시도 로그

  - <무엇을 시도> - <왜 버렸나 | 결과> - <커밋 hash>

* 사전 지식(prerequisite)                  ← 낯선 영역 없으면 섹션 통째 생략

** <개념명>

   - 무엇: <한 줄>
   - 독자가 아는 것으로는: <주력 언어·버전에서 같은 일을 하던 방식 | 해당 없음>
   - 왜 여기 필요했나: <한 줄>
   - 등장 위치: [[file:/abs/path/foo.cpp::40][foo.cpp:40]]

* 핵심 코드 워크스루

** <논리 단위 제목>

   - <설명 한 줄>
   [[file:/abs/path/foo.cpp::40][foo.cpp:40]]
   #+begin_src cpp
   <근거 라인만>
   #+end_src
   - <이 코드가 trade-off의 어느 쪽을 택한 것인지>

* TODO 확인 질문

** TODO <대안 B를 택했다면 무엇이 달라지나>

*** 힌트 1

    - <문서 안 재료 - trade-off 표의 어느 축 | 시도 로그 n번째>

*** 힌트 2

    - <이어야 할 코드 위치> - [[file:/abs/path/foo.cpp::40][foo.cpp:40]]

*** 답

    - <정답 한두 문장>

* 수동 확인 필요

  - <확인할 것> - <확인 방법>       ← 없으면 "없음" 한 줄
```

## org 작성 규칙

- 한 항목 = 한 bullet, 물리적으로 한 줄(문장 중간 하드 줄바꿈 금지 - 길어도 한 줄, 표시는 emacs soft-wrap).
- org verbatim(`=...=`) 안에 `=` 문자를 넣지 않는다(구문이 깨진다).
- 한글 조사가 바로 뒤에 붙는 자리에는 마크업을 쓰지 않는다 - `~Workout~에`는 org가 마크업으로 인식하지 못해 export에서 깨진다. `Workout 모델에`처럼 조사가 붙지 않게 문장을 쓰고, 부득이하면 `~Workout~ 에`로 한 칸 띄운다.
- 헤딩 아래 본문은 별 개수 + 1칸 들여쓴다(`*` → 2칸, `**` → 3칸, `***` → 4칸). 포매팅 단계가 자동으로 맞추므로 초안에서 손으로 맞출 필요는 없다.
- org 테이블은 표시 폭 100 컬럼 안팎, 긴 셀은 아래 행으로 이어 쓰고 항목 사이에 구분선 `|---+---|`.
