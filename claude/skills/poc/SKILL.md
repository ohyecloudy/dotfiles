# PoC

일을 정의해 넘기기 **전에** "되는가, 어떤 trade-off인가"를 결과로 확인한다. 산출물은 둘이다.

- 동작하는 완성물 - 현재 작업 트리에 커밋된 코드
- 정리 문서 - 결론, trade-off, 검증 근거, 핵심 코드 학습. 본인 판단·학습용 독립 문서로, spec·티켓과 연계하지 않는다

속도가 우선이다. 코드 품질은 본 구현 몫이므로 TDD·`/code-review`는 하지 않는다. 대신 **결론마다 실행 증거**를 남긴다 - 증거 없는 결론은 정리 문서의 신뢰를 깎는다.

## 전제

- 대화 맥락에 `/grill-for-poc`으로 합의한 4개 합의 항목이 있어야 한다. 없거나 비었으면 `/grill-for-poc`을 먼저 하라고 안내하고 멈춘다. 빈칸을 추측으로 채우지 않는다.
- 착수 후에는 **비인터랙티브**로 진행한다. 합의는 grill에서 끝났다 - 종료 조건에 닿을 때까지 사용자를 붙잡지 않는다.
- git 저장소가 아니면 착수 전에 알리고 멈춘다(커밋 단위 기록이 시도 로그·학습 섹션의 전제).

## 합의 항목

합의 항목 어휘의 정본. `grill-for-poc`이 여기를 참조한다.

- 검증할 질문 - 예/아니오 또는 수치로 답할 수 있는 형태
- 완료 조건 - 관측 가능한 실행 증거
- 비교할 대안 - 대안별 `구현`/`분석만` 지정 + 비교 축
- 범위 밖

## 저장 위치 판정

먼저 저장소 루트를 보고 in-repo인지 외부(`~`)인지 결정한다. 전체 규칙은 [project-docs-storage.md](../shared/project-docs-storage.md) 참고. 정리 문서는 `docs/pocs/<slug>/poc.org`(`<slug>` = 검증할 질문 주제 kebab), 외부 모드면 `~/project-docs/<정규화 경로>/docs/pocs/<slug>/poc.org`.

## PoC status

PoC status 어휘의 정본. 파일 맨 위 property drawer의 `:STATUS:` 속성에 쓰고, 허용값은 같은 drawer의 `:STATUS_ALL:`에 공백으로 나열한다. status를 바꿀 때는 `:STATUS:` 줄만 고친다.

- `in-progress` - 착수 초기값
- `done` - 검증할 질문에 답이 나옴. 완료 조건 충족과 가설 반증("불가 + 근거") 모두 여기
- `blocked` - 막힘. 부분 결론 + 막힌 원인
- `needs-human` - 결론은 났으나 사람만 확인할 수 있는 실행 증거가 남음

## 컨텍스트 분담

메인은 오케스트레이터다 - 합의, 골격, 종합, 보고만 한다. 무거운 작업(구현 루프, 코드 탐색, `explain-change` JSON)은 서브에이전트에 맡겨 메인 컨텍스트를 가볍게 유지한다. 원칙: **상세는 서브에이전트가 poc.org에 직접 쓰고, 메인에는 요약만 돌아온다.** 메인은 필요한 섹션만 Read한다.

- 착수, 결론, 확인 질문, 포매팅, 보고 - 메인
- `구현` 대안 - 대안마다 `general-purpose` 1개, 순차
- `분석만` 대안 - `Explore` 1개
- 학습 섹션 - `general-purpose` 1개 (독자 프로필 판정은 메인)

## 프로세스

### 1. 착수

- `git rev-parse HEAD`로 **시작 커밋**을 기록한다. 학습 섹션 범위의 기준이다.
- 아래 템플릿으로 poc.org 골격을 만든다: drawer(`in-progress`, `:CREATED:`, `:BASE_COMMIT:`) + `* 합의` 섹션. 나머지 섹션은 heading만 둔다.
- 골격을 착수 직후 쓰는 이유: `* 합의`가 서브에이전트가 읽는 정본이고, 시도 로그·검증 근거를 서브에이전트가 이 파일에 누적한다.

### 2. `구현` 대안

`구현` 지정 대안마다 Agent 도구로 `general-purpose` 서브에이전트를 하나씩 **순차로** 띄운다. 같은 작업 트리·브랜치에서 커밋하므로 병렬 불가.

- 프롬프트: [alternative-worker.md](alternative-worker.md)의 절대 경로(이 절차를 따르라고 지시), poc.org 절대 경로, 대안명, 저장소 위치, 시작 커밋. 합의를 옮겨 쓰지 않는다(worker가 poc.org에서 읽는다). 앞선 대안의 결과도 넘기지 않는다.
- 반환 요약(대안, 종료, 답, 실측, 커밋, 수동 확인 필요)을 대안별로 보관한다 - 결론·trade-off 재료다.
- 대안은 독립 판정한다. 한 대안이 `blocked`·`disproved`여도 남은 대안을 계속 돌린다 - 막힌 이유 자체가 trade-off 재료다. 앞 대안이 질문에 답을 냈어도 나머지를 생략하지 않는다(`구현` 지정 = 실측 비교가 필요하다는 합의).
- 서브에이전트가 요약 없이 끝나면 poc.org `* 시도 로그`만 Read해 그 대안을 `blocked`로 처리하고, 원인 한 줄을 시도 로그에 추가한다.

### 3. `분석만` 대안

`분석만` 대안이 있으면 `구현` 대안이 끝난 뒤 Agent 도구로 `Explore` 서브에이전트 **1개**에 모두 묶어 맡긴다. 프롬프트 골자:

- 저장소 위치, poc.org 절대 경로(`* 합의`를 읽게)
- 분석할 대안 목록과 비교 축, 2단계에서 실측된 축별 값(같은 축으로 비교하게)
- 코드·문서 근거로만 비교하고 파일을 쓰지 말 것
- 반환: 대안별로 비교 축마다 값 한 줄 + 근거 위치(`절대경로:라인`)

Explore는 파일을 쓸 수 없으므로 메인이 반환값을 `* 시도 로그`에 대안별 한 줄로 기록한다(trade-off `(분석)` 셀 재료).

### 4. 학습 섹션

- 독자 프로필: [reader-profile.md](../shared/reader-profile.md)로 PoC 코드의 언어·버전·프레임워크를 판정하고, 빠진 프로필은 물어 기록한 뒤 **낯선 영역**을 정한다. 비인터랙티브 원칙의 유일한 예외 - 이미 기록돼 있으면 묻지 않는다. 서브에이전트는 사용자와 대화할 수 없으므로 묻기는 여기서 끝낸다.
- Agent 도구로 `general-purpose` 서브에이전트에 [learning-worker.md](learning-worker.md)를 맡긴다. 프롬프트: worker 파일 절대 경로, poc.org 절대 경로, 범위 `<시작 커밋>..HEAD`, 저장소 위치, 낯선 영역(없으면 생략).
- worker가 `* 사전 지식`, `* 핵심 코드 워크스루`를 직접 채운다. 실패 반환이면 두 섹션에 "생성 실패 - <원인>" 한 줄을 남기고 진행한다.

### 5. 결론 작성

poc.org `* 검증 근거`, `* 시도 로그`, `* 수동 확인 필요`를 Read하고 2-3단계 요약과 합쳐 `* 결론`, `* trade-off`를 채운다. trade-off 표의 각 셀에 근거가 `실측`인지 `분석`인지 표시한다 - 추측이 실측처럼 읽히지 않게.

`:STATUS:`는 대안별 결과를 종합해 정한다.

- 검증할 질문에 답이 나옴(어느 대안이든 완료 조건 충족, 또는 반증으로 답이 확정) -> `done`
- 답이 안 나옴 + `blocked` 대안이 있음 -> `blocked`. 부분 결론 + 막힌 원인
- `done`인데 `* 수동 확인 필요` 항목이 남음 -> `needs-human`

### 6. 확인 질문

`* TODO 확인 질문`을 trade-off 결정 지점 위주로 2~4개 쓴다. trade-off 표가 확정된 뒤라야 결정 지점이 보인다. `힌트 2`의 코드 위치는 `* 핵심 코드 워크스루` 섹션만 Read해 가져온다. 막히면 `힌트 1` -> `힌트 2` -> `답` 순으로 펼친다.

### 7. 포매팅

먼저 [code-locations.md](../shared/code-locations.md)의 검사를 poc.org에 실행하고 출력이 없을 때까지 고친다. 그다음 [org-formatting.md](../shared/org-formatting.md)의 정렬을 실행한다.

### 8. 문서 커밋

- in-repo면 poc.org를 커밋한다(별도 `docs:` 커밋).
- 외부 모드(`~/project-docs/...`)면 파일만 두고 커밋하지 않는다.

### 9. 보고

채팅에는 문서 전문을 쏟지 말고 아래만 출력한다.

- 검증할 질문에 대한 답 한 줄
- status
- `수동 확인 필요` 항목(있으면)
- 커밋 범위 `<시작 커밋>..HEAD`
- poc.org **절대 경로** (홈 아래면 `~`로 줄임, Windows는 `D:/...`처럼 슬래시)

## 템플릿

```org
:PROPERTIES:
:STATUS_ALL: in-progress done blocked needs-human
:STATUS:   in-progress
:CREATED:  [<YYYY-MM-DD> <영어 요일 약어: Mon..Sun>]
:BASE_COMMIT: <시작 커밋 hash>
:END:
#+title: PoC - <검증할 질문 요약>

* 결론

  - 답: <예 | 아니오 | 수치 | 조건부> - <한 줄>
  - 핵심 근거: <실측 결과 한 줄> - <커밋 hash>

* 합의

  - 검증할 질문: <...>
  - 완료 조건: <...>
  - 비교할 대안
    - <대안 A> - 구현
    - <대안 B> - 분석만
  - 비교 축: <성능, 메모리, 구현 복잡도 ...>
  - 범위 밖: <...>

* trade-off

  | 축     | 대안 A           | 대안 B           |
  |--------+------------------+------------------|
  | <축 1> | <값> (실측)      | <값> (분석)      |
  |--------+------------------+------------------|

* 검증 근거

  - <결론 항목> - <실행 명령> -> <출력 요약> - <커밋 hash>

* 시도 로그

  - <무엇을 시도> - <왜 버렸나 | 결과> - <커밋 hash>

* 사전 지식(prerequisite)                  ← 낯선 영역 없으면 섹션 통째 생략

** <개념명>

   - 무엇: <한 줄>
   - 독자가 아는 것으로는: <주력 언어·버전에서 같은 일을 하던 방식 | 해당 없음>
   - 왜 여기 필요했나: <한 줄>
   - 등장 위치: [[file:/abs/path/foo.cpp::40][foo.cpp:40]]

* 핵심 코드 워크스루

** <논리 단위 제목>

   - <설명 한 줄>
   [[file:/abs/path/foo.cpp::40][foo.cpp:40]]
   #+begin_src cpp
   <근거 라인만>
   #+end_src
   - <이 코드가 trade-off의 어느 쪽을 택한 것인지>

* TODO 확인 질문

** TODO <대안 B를 택했다면 무엇이 달라지나>

*** 힌트 1

    - <문서 안 재료 - trade-off 표의 어느 축 | 시도 로그 n번째>

*** 힌트 2

    - <이어야 할 코드 위치> - [[file:/abs/path/foo.cpp::40][foo.cpp:40]]

*** 답

    - <정답 한두 문장>

* 수동 확인 필요

  - <확인할 것> - <확인 방법>       ← 없으면 "없음" 한 줄
```

## org 작성 규칙

- 한 항목 = 한 bullet, 물리적으로 한 줄(문장 중간 하드 줄바꿈 금지 - 길어도 한 줄, 표시는 emacs soft-wrap).
- org verbatim(`=...=`) 안에 `=` 문자를 넣지 않는다(구문이 깨진다).
- 한글 조사가 바로 뒤에 붙는 자리에는 마크업을 쓰지 않는다 - `~Workout~에`는 org가 마크업으로 인식하지 못해 export에서 깨진다. `Workout 모델에`처럼 조사가 붙지 않게 문장을 쓰고, 부득이하면 `~Workout~ 에`로 한 칸 띄운다.
- 헤딩 아래 본문은 별 개수 + 1칸 들여쓴다(`*` → 2칸, `**` → 3칸, `***` → 4칸). 포매팅 단계가 자동으로 맞추므로 초안에서 손으로 맞출 필요는 없다.
- org 테이블은 표시 폭 100 컬럼 안팎, 긴 셀은 아래 행으로 이어 쓰고 항목 사이에 구분선 `|---+---|`.
