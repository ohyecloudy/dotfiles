# Code Tour

처음 보는 코드베이스나 push 전 커밋을 **사용자가 직접 찾아 읽으며** 이해하도록 안내하는 문서를 만든다. 핵심은 확인 질문 - 사용자가 질문 heading 아래 답을 쓰고, 이 스킬로 검증받는 루프를 돈다.

## 경계

- `walkthrough`와 다르다. 그쪽은 이번 세션에서 만든 변경을 저자 세션 정보로 리뷰어에게 설명하고, 이쪽은 세션 컨텍스트 없이(콜드) 기존 코드나 커밋을 학습한다. 변경 모드도 세션이 아는 "왜"를 쓰지 않는다 - 커밋·코드·테스트·ADR로 확정되는 것만.
- **정답을 먼저 주지 않는다.** 직접 찾아야 머리에 남는다. 정답은 문서에 있되 접힌 `**** 답` 서브heading 뒤에 둔다 - 펼치기 전에 `힌트 1` → `힌트 2` 순서로 스스로 찾게 한다. 펼치는 시점은 사용자 선택. 검토는 틀림이면 힌트만 준다 - 사용자가 아직 `**** 답`을 펼치지 않았을 수 있다. 채팅으로는 사용자가 명시적으로 요청할 때만 정답을 공개한다.
- 상태 전환(`TODO` → `DONE`)은 사용자 몫. 스킬은 heading을 `TODO`로 만들기만 하고 바꾸지 않는다.

## 모드 분기

- **code-tour 문서의 선택 영역이 있으면 검증 모드.** 인자나 IDE 첨부 컨텍스트에 `<파일>:<시작>-<끝>` 형태의 선택이 있고, 그 파일이 `~/code-tour/` 아래 `.org`인 경우. → §검증 모드
- **인자가 커밋을 가리키면 변경 모드.** `push`이거나, `..`를 포함하거나, `git rev-parse --verify <인자>^{commit}`이 성공하는 경우. → §변경 모드
  - 같은 이름의 경로가 저장소에 있으면 경로로 보고 생성 모드 - 기존 동작을 지킨다.
- **그 밖에는 생성 모드.** 인자는 범위로 해석. → §생성 모드
  - 소스 파일 선택은 "이 부분을 따라 읽고 싶다"는 뜻이고, IDE가 선택을 자동 첨부하기도 한다 - 검증 모드로 빠지지 않게 한다.

## 생성 모드

### 1. 범위와 언어 판정

- **범위**: 인자의 경로·주제. 인자가 없고 소스 파일 선택 영역이 있으면 그 영역. 둘 다 없으면 저장소 전체.
  - 부분 범위면 그 범위에 맞게 `전체 그림`을 줄이고 단계 수도 줄인다. 범위에 해당 없는 단계(예: UI가 없는 모듈의 UI 단계)는 빼되 순서는 유지.
- **독자 프로필**: [reader-profile.md](../shared/reader-profile.md)로 대상 언어·버전·프레임워크를 판정하고, 빠진 프로필은 물어 기록한 뒤 **낯선 영역**을 정한다. 대상 언어가 여러 개면 주력 하나를 대상으로, 나머지는 해당 단계에서만 언급.
- **낯선 영역을 문서에 싣는 위치**
  - 언어: 낯선 영역이 없으면(같은 언어, 독자 버전 이상) 언어 쪽 전제·포인트·대응표는 "해당 없음 - 주력 언어와 동일" 한 줄로. 버전 차이만 있으면 대응표 제목은 `<독자 버전> ↔ <대상 버전>`.
  - 프레임워크 낮음: `0단계 전제`에 그 프레임워크의 기반 절을 넣고, 각 단계 `언어·프레임워크 포인트`에서도 그 단계에 처음 나오는 프레임워크 기능을 설명한다.
  - 프레임워크 보통: 기반 절 없이 단계 포인트에서만.
  - 프레임워크 높음: 설명 생략. 관용과 다르게 쓴 곳만 `설계 포인트`로.

### 2. 탐색

- `CONTEXT.org`(다중 컨텍스트면 `CONTEXT-MAP.org` → 각 `CONTEXT.org`), `docs/adr/`, `docs/specs/`, 티켓 문서가 있으면 읽어 용어와 결정의 근거를 잡는다. **읽기만** 한다.
- 문서 위치는 [project-docs-storage.md](../shared/project-docs-storage.md)로 판정한다 - 외부 모드면 위 문서들은 `~/project-docs/<정규화된 저장소 절대경로>/` 아래 같은 상대 경로에 있다.
  - 외부 모드여도 저장소 안의 upstream 문서(`docs/adr/` 등)는 함께 읽는다. 두 곳 모두 있으면 둘 다 근거로 쓴다.
  - 인용은 실제로 읽은 쪽의 절대 경로 링크로. 외부 문서는 저장소와 이력이 따로라 기준 커밋이 적용되지 않는다 - 라인 링크 뒤에 heading 이름을 평문으로 적어 라인이 어긋나도 찾을 수 있게 한다(`[[file:/abs/CONTEXT.org::61][CONTEXT.org:61]] "도구와 작업"`).
- 프로젝트 `CLAUDE.md`의 규칙(테스트 정의 등)도 확인 질문 재료가 된다.
- 기준 커밋: `git rev-parse --short HEAD`. 라인 번호가 모두 이 커밋 기준이라는 사실을 `사용법`에 기록한다. 커밋되지 않은 변경이 범위 안에 있으면 그 사실도 함께 적는다.

### 3. 단계 구성

단계 순서는 고정 - 의존 방향을 따라 아래에서 위로 쌓아야 앞 단계 어휘로 다음 단계를 읽을 수 있다.

1. 어휘 - `CONTEXT`·ADR. 코드보다 먼저
2. 순수 모델 - 데이터 구조, 엔티티
3. 도메인 규칙 - 판정·계산 함수
4. 소유자/상태 - 상태를 들고 변경을 조율하는 객체
5. 경계 어댑터 - 직렬화, OS·네트워크·저장소 경계
6. UI
7. 테스트 - 설계가 실제로 고정된 곳

코드베이스에 따라 한 항목이 여러 단계로 나뉘어도 된다(예: 경계 어댑터 → 메시지 DTO + 링크). 해당 없는 항목은 뺀다.

### 4. 단계 내용

각 단계 = `먼저 읽을 것` → `코드` → `설계 포인트` → `언어·프레임워크 포인트` → `확인 질문`. 해당 없는 하위 섹션은 생략(확인 질문은 생략 불가). `0단계 전제`는 예외 - 설명만 두고 확인 질문을 만들지 않는다. 언어·프레임워크 일반 지식이라 이 코드로 답이 하나로 정해지지 않고, 이해 여부는 이후 단계 질문에서 드러난다.

- **먼저 읽을 것**: 이 단계 전에 읽을 ADR·spec·CONTEXT 절. 절대 경로 링크로.
- **코드**: 읽을 순서대로 번호 매긴 `[[file:절대경로::라인][파일명:라인]] =심볼= - <왜 여기>`. 선언부 → 진입 함수 → 핵심 함수 순. 같은 파일의 여러 위치는 그 항목 아래 하위 bullet로 펼치고 각 줄에 전체 경로를 쓴다([code-locations.md](../shared/code-locations.md)).
- **설계 포인트**: 코드에 박힌 결정과 그 이유. 주석·ADR에 근거가 있는 것만. `*굵게*` 한 구절 + 설명.
- **언어·프레임워크 포인트**: 언어는 주력 언어(버전 포함)에 **직접 대응이 없거나 의미가 다른 것만** - 주력 언어에도 똑같이 있는 문법은 소음이다. 각 항목에 주력 언어의 가장 가까운 개념을 `≈` 로 붙인다. 프레임워크는 §1 숙련도별 분량을 따른다. 모든 항목에 이 코드의 실제 등장 위치 하나를 단다.
- **확인 질문**: §5

### 5. 확인 질문

질문이 이 문서의 핵심 산출물. 사용자가 그 heading 아래 답을 쓰고 검증 모드로 확인받는다 - 그래서 bullet이 아니라 heading이어야 한다.

- 형식: `** TODO 확인 질문` 아래 질문마다 `*** <질문>` heading, 그 아래 `**** 힌트 1` / `**** 힌트 2` / `**** 답` 서브heading(이 순서, 상태 키워드 없음). 사용자 답은 질문 본문, 즉 `**** 힌트 1` 위에 쓴다. 서브heading이라 문서를 열면 접혀 있다.
- heading 하나에 물음 하나, 한 문장. "A는 무엇이고, B는 어디이며, 왜 C인가"처럼 묶으면 heading이 문단이 되고 검증 판정도 흐려진다 - 나눠서 별도 질문으로.
- 단계당 2~3개. 아래 세 종류 중 **최소 2종**을 섞는다 - 한 종류만이면 같은 근육만 쓴다.
  - 이유: "왜 X는 Y가 아니라 Z인가"
  - 반사실: "X를 없애거나 바꾸면 무엇이 깨지나" - 실제로 깨지는 테스트가 있는 것만. 정답 = 깨지는 테스트 + 그 테스트가 고정한 규칙. 테스트로 고정되지 않은 동작은 답이 추론에 기대 판정이 흐려진다. 출제 시 코드를 바꿔 실행하지 않고 테스트를 읽어 확정한다(저장소 무변경, 빌드 비용 회피). 깨질 테스트를 특정 못 하면 버린다.
  - 추적: "A가 일어나면 B까지 어떤 경로로, 무엇이 실려 가나"
- 어휘 단계는 예외 - 1~2개, 이유 질문만. 용어·ADR엔 깨질 테스트도 호출 경로도 없다. 대신 용어 정의와 ADR 근거를 이어야 답이 나오게 한다(어휘는 이후 단계에서 계속 쓰며 확인된다). 힌트 1 = CONTEXT 용어 정의, 힌트 2 = ADR 근거.
- **확정 가능한 것만.** 코드·주석·테스트·ADR로 답이 하나로 정해져야 검증할 수 있다. 의견·취향을 묻지 않는다.
- **최소 두 곳을 이어야 답이 나오는 것.** 한 줄 주석을 그대로 옮기면 끝나는 질문은 찾기 연습이지 이해 확인이 아니다.
- **정답은 `**** 답`에 기록한다.** 출제 시점에 정답을 스스로 확정한다 - 확정 못 하면 그 질문은 버린다.
- 모든 질문에 힌트 1·2·답 필수. 각각 한두 bullet.
  - **힌트 1**: 어디를 볼지 - 답에 필요한 두 곳 중 한 곳, 파일·심볼 수준. 힌트 1만으로 답이 확정되면 안 된다. 반사실 질문은 깨질 테스트의 **파일 링크만**(`[[file:/abs/path/FooTests.swift][FooTests.swift]]`, 라인 없음) - 라인까지 주면 깨지는 테스트, 즉 정답 절반을 알려 준다.
  - **힌트 2**: 무엇을 이어야 하는지 - 나머지 한 곳, 라인 링크 허용. 정답 문장은 쓰지 않는다.
  - **답**: 질문이 묻는 핵심을 빠짐없이 한두 문장 + 근거 org 링크. 반사실은 깨지는 테스트 + 그 테스트가 고정한 규칙.

```org
** TODO 확인 질문

*** 워치가 같은 완료를 두 번 보냈을 때 두 번째 ack에는 무엇이 실리는가

**** 힌트 1

     - <두 곳 중 한 곳 - 파일·심볼>

**** 힌트 2

     - <나머지 한 곳 - 라인 링크>

**** 답

     - <정답 한두 문장> - [[file:/abs/path::line][파일명:line]]

*** =publish= 에서 종료 정보를 이어 싣지 않으면 어떤 테스트가 깨지나

**** 힌트 1

     - [[file:/abs/path/Tests/HealthRecordingIntegrationTests.swift][HealthRecordingIntegrationTests.swift]]

**** 힌트 2

     - <테스트가 확인하는 값이 만들어지는 곳 - 라인 링크>

**** 답

     - <깨지는 테스트 + 고정한 규칙> - [[file:/abs/path::line][파일명:line]]
```

### 6. 문서 작성

`~/code-tour/YYYY-MM-DD-HHMM-<slug>.org`에 쓴다(`<slug>` = 저장소명 또는 범위 kebab). 디렉터리가 없으면 만든다. 문서가 저장소 밖에 있으므로 ADR·spec·ticket·CONTEXT 인용도 전부 절대 경로.

골격은 고정. 단계 heading은 전부 `TODO`.

```org
#+title: <저장소> 코드 따라 읽기 - <범위> (<주력 언어> 프로그래머용)

<이 문서가 설계 문서를 대신하지 않는다는 한 줄 - 이유는 ADR에, 여기는 그 결정이 코드 어디에 있는지>

* TODO 사용법

  - 단계를 순서대로 진행. 각 단계는 "먼저 읽을 것 → 코드 → 설계 포인트 → 언어·프레임워크 포인트 → 확인 질문"
  - 위치는 org 링크 - =]l= / =[l= 로 이동, =RET= 로 열기(=C-c C-RET= 다른 창), =C-o= 로 복귀
  - 라인 번호는 커밋 =<sha>= 기준. 어긋나면 함께 적힌 심볼 이름으로 검색
  - 확인 질문 heading 아래(=힌트 1= 위) 답을 쓰고, 그 영역을 선택해 =/code-tour= 로 검증
  - 막히면 =힌트 1= → =힌트 2= → =답= 순으로 펼침
  - 해당 영역의 단위 테스트도 단서 - 테스트 이름이 곧 규칙 목록

* TODO 전체 그림 먼저

** 한 문장 요약

   <시스템의 정체 한 문장>

** 계층도

   #+begin_src mermaid :file ~/code-tour/<slug>-layers.png :width "2048"
   <계층·의존 방향 flowchart>
   #+end_src

   - <계층도를 읽는 법 1~2줄>

** 디렉터리와 타깃

   - [[file:/abs/path/dir/][dir/]] - <역할>

* TODO 0단계: 읽기 전 전제 - <대상 언어>, <숙련도 낮은 프레임워크>

** TODO 0-1. <전제>

   - <설명 - 주력 언어와의 차이 중심>

** TODO 0-N. <프레임워크> 기반: <주제>    ← 숙련도 낮음인 프레임워크만

   - <설명 - 매크로가 생성하는 것, 수명, 실행 모델 등>

* TODO 1단계: <제목>
```

- `0단계 전제`: 언어는 모르면 코드 곳곳이 소음으로 보이는 것 3~6개. 숙련도 낮음인 프레임워크마다 기반 절 2~5개. 각 단계의 `언어·프레임워크 포인트`에서 반복하지 않는다.
- 시나리오: 단계를 가로지르는 핵심 흐름 1~4개. 각 화살표가 실제 호출이어야 한다.
- 대응표: 문서에 등장한 언어 포인트의 요약(프레임워크 항목은 주력 언어 쪽 대응이 있을 때만). 새 항목을 여기서 처음 소개하지 않는다.

## 변경 모드

push 전에 커밋을 **이해했는지** 확인한다. 질문 대상은 커밋이 바꾼 동작·이유·영향이고, 주변 코드는 답에 필요한 만큼만 읽힌다. 생성 모드의 규칙을 따르되 아래 차이만 적용한다.

### 1. 범위

- `push` → `@{u}..HEAD`. 커밋 hash면 그 커밋 하나, `a..b`면 그 범위.
- `@{u}`가 없으면(upstream 미설정) 추측하지 말고 사용자에게 범위를 묻는다.
- 범위가 비면 문서를 만들지 않고 "대상 없음"으로 보고만 한다.
- 커밋되지 않은 변경은 대상이 아니다. 있으면 그 사실만 `사용법`에 적는다.
- 독자 프로필·낯선 영역은 생성 모드 §1 그대로. 대상 언어는 범위 전체 diff 기준.

### 2. 그룹 묶기

스킬이 자동으로 묶고 확인을 묻지 않는다 - 결과는 문서 `사용법`과 채팅 보고에 드러나므로, 마음에 안 들면 사용자가 명시 범위로 다시 부른다.

- 판정 재료는 `git log --numstat <범위>`와 커밋 subject의 conventional type. 이 단계에서는 `explain-change`를 부르지 않는다(묶기 전에 커밋마다 분석하면 비용이 그룹 수가 아니라 커밋 수에 비례한다).
- **간단한 커밋** = 아래 중 하나
  - 동작 변화 없음: 주석·문서·포매팅·rename만, `chore`/`style` 계열
  - 소규모: 테스트 제외 변경 라인 합계 20줄 이하이고 새 공개 심볼(함수·타입·명령·키 바인딩 등)이 없음
- **묶는 규칙**
  - 간단한 커밋은 같은 주제(subsystem - scope나 건드린 디렉터리)의 인접 커밋과 한 그룹. 주제가 다르면 간단해도 따로.
  - 앞선 커밋의 같은 파일·심볼을 고치는 후속 커밋(fix-up)은 그 커밋 그룹에 흡수한다.
  - 간단하지 않은 커밋끼리는 묶지 않는다 - 커밋당 한 그룹.
  - 그룹 순서는 커밋 순서(그룹의 첫 커밋 기준).

### 3. 변경 분석

그룹마다 `explain-change`를 호출한다. 그룹이 둘 이상이면 서브에이전트로 병렬 - 코어는 사용자와 대화하지 않으므로 가능하다.

- 넘기는 것: 그룹이 연속 커밋이면 범위 `<첫 커밋>^..<끝 커밋>`, fix-up 흡수로 비연속이면 그 커밋들의 `git show` diff를 이어 붙인 텍스트. 저장소 위치와 §1의 낯선 영역도 함께. 다이어그램은 요청하지 않는다.
- 결과 사용
  - `reading_order` → `바뀐 곳`
  - `prerequisites` → `언어·프레임워크 포인트`, 여러 그룹에 걸치는 `reader-unfamiliar`는 `0단계 전제`로 올린다
  - `impact` → 추적 질문 재료
  - 결과의 경로는 맨 경로 - 문서에 옮길 때 org 링크로 바꾼다([code-locations.md](../shared/code-locations.md))
- 질문 출제와 정답 확정(테스트 읽기 포함)은 코어가 아니라 이 스킬 몫이다.

### 4. 확인 질문

생성 모드 §5를 따르되 다음이 다르다.

- 질문 종류에 **전/후 대비**를 더한다: "이 커밋 전엔 X일 때 무엇이 일어났고 지금은 무엇인가". 정답이 `git show <sha>`로 하나로 정해지므로 테스트가 없는 변경에도 출제할 수 있다. 힌트 1 = 바뀐 위치, 힌트 2 = `git show <sha>`에서 "전" 쪽을 확인할 지점(어느 파일의 hunk인지).
- 이유·반사실·추적·전/후 대비 중 **최소 2종**. 반사실은 생성 모드 규칙 그대로 - 깨지는 테스트를 특정할 수 있을 때만.
- 질문 수: 일반 그룹 2~3개, 간단한 그룹 1~2개.
- 질문 heading에 커밋 sha를 넣지 않는다 - 그룹 heading의 `커밋`에서 찾는다.

### 5. 문서 작성

`~/code-tour/YYYY-MM-DD-HHMM-<저장소>-push.org`에 쓴다(명시 범위로 불렀어도 같은 이름 규칙). 호출 1회 = 문서 1개, 그룹마다 top-level heading. 라인 번호는 HEAD(변경 후) 기준.

생성 모드의 `전체 그림`, 1~7단계 고정 순서, `시나리오로 따라가기`, `다음에 해볼 것`은 싣지 않는다 - 변경 단위에서는 무겁고 그룹 간 중복이 크다.

```org
#+title: <저장소> 변경 따라 읽기 - <base>..<head> (<주력 언어> 프로그래머용)

<이 문서가 커밋 메시지·ADR을 대신하지 않는다는 한 줄 - 여기는 그 변경이 코드 어디에 있는지>

* TODO 사용법

  - 그룹을 순서대로 진행. 각 그룹은 "커밋 → 바뀐 곳 → 설계 포인트 → 언어·프레임워크 포인트 → 확인 질문"
  - 위치는 org 링크 - =]l= / =[l= 로 이동, =RET= 로 열기(=C-c C-RET= 다른 창), =C-o= 로 복귀
  - 라인 번호는 커밋 =<HEAD sha>= 기준(변경 후). 어긋나면 함께 적힌 심볼 이름으로 검색
  - 확인 질문 heading 아래(=힌트 1= 위) 답을 쓰고, 그 영역을 선택해 =/code-tour= 로 검증
  - 막히면 =힌트 1= → =힌트 2= → =답= 순으로 펼침
  - 그룹 구성
    - 그룹 1: <주제> - =<sha>= <subject>, =<sha>= <subject>
    - 그룹 2: <주제> - =<sha>= <subject>

* TODO 0단계: 읽기 전 전제 - <대상 언어>, <숙련도 낮은 프레임워크>    ← 낯선 영역이 있을 때만

** TODO 0-1. <전제>

   - <설명 - 주력 언어와의 차이 중심>

* TODO 그룹 1: <주제>

** 커밋

   - =<sha>= <subject> - diff: git show <sha>

** TODO 바뀐 곳

   1. [[file:/abs/path/foo.el::42][foo.el:42]] =symbol= - <무엇이 바뀌었나 한 줄>

** TODO 설계 포인트

** TODO 언어·프레임워크 포인트

** TODO 확인 질문

*** <질문>

**** 힌트 1

**** 힌트 2

**** 답

* <주력> ↔ <대상> 대응 요약    ← 언어 포인트가 있을 때만

  | <대상>  | <주력>에 가장 가까운 것 | 주의 |
  |---------+-------------------------+------|
```

- `바뀐 곳`: 읽을 순서대로 번호. 형식은 생성 모드 §4 `코드`와 같고, `<왜 여기>` 대신 무엇이 바뀌었나를 쓴다. 삭제만 된 것은 위치 대신 "삭제: =symbol= (파일 경로)"로.
- `설계 포인트`: 근거는 커밋 메시지 본문·주석·ADR만. 세션 기억으로 채우지 않는다(§경계).
- 해당 없는 하위 섹션은 생략(확인 질문은 생략 불가) - 생성 모드 §4와 같다.

### 6. 포매팅·보고

- §포매팅 실행.
- 채팅에는 문서 전문 대신 아래만: 범위, 그룹 구성(그룹당 한 줄 - 주제와 sha 목록), 질문 수, 생성한 org 파일의 **절대 경로**.

## 검증 모드

### 1. 대상 추출

- 선택 영역 안의 `*** <질문>` heading만 대상. 영역 밖 질문은 건드리지 않는다.
- 영역 안에 질문 heading이 없으면(답 본문만 선택 등) 선택 시작 라인을 감싸는 가장 가까운 상위 `***` 질문 heading 하나를 대상으로 삼는다. 그것도 없으면(질문 영역 밖) 검토를 쓰지 않고 "대상 없음"으로 보고만 한다.
- 답 = 질문 heading 아래 본문에서 `**** 힌트 1`/`**** 힌트 2`/`**** 답`/`**** 검토` 서브트리를 뺀 것.
- 답이 비어 있으면 검토를 쓰지 않고 "답 없음"으로 보고만 한다.

### 2. 정답 재도출

- 판정 기준은 문서의 `**** 답`이 아니라 **지금 코드(working tree)에서** 다시 도출한 정답이다 - 사용자도 링크로 지금 파일을 열어 읽고 답을 쓰고, `**** 답`은 출제 시점 기준이라 낡을 수 있다. 질문·힌트·사용자 답이 가리키는 위치를 실제로 열어 확인한다 - 답이 그럴듯해 보인다는 이유로 판정하지 않는다.
- 재도출 정답이 `**** 답`과 다르면 검토에 `문서 답 낡음`을 적는다. `**** 답` 자체는 고치지 않는다 - 문서 재생성은 사용자 몫.
  - 변경 모드 문서의 전/후 대비 질문은 "전" 쪽을 그 그룹 `커밋`의 `git show <sha>`로 도출한다. sha가 지금 이력에 없으면(rebase 등) `전제 변경`.
- `사용법`의 기준 커밋과 `git rev-parse --short HEAD`가 다르면 검토에 그 사실을 적는다(라인·동작이 바뀌었을 수 있다).
- 질문의 전제(가리키는 심볼·테스트)가 지금 코드에 없으면 판정을 `전제 변경`으로 하고 무엇이 사라졌는지만 적는다. 질문을 고치거나 재출제하지 않는다 - 문서 재생성은 사용자 몫.

### 3. 검토 작성

질문 heading 서브트리 끝(`**** 답` 뒤)에 `**** 검토`를 쓴다. 이미 있으면 덮어쓴다(이전 검토는 지운다).

```org
**** 검토

     - 판정: 맞음 | 부분 | 틀림 | 전제 변경
     - 맞음: <맞은 부분>
     - 어긋남: <틀린 문장 지적>
     - 볼 곳: [[file:/abs/path::line][파일명:line]]
     - 문서 답 낡음: <재도출 정답>   ← `**** 답`과 다를 때만
     - 기준: 문서 =<sha>= / HEAD =<sha>=   ← 다를 때만
```

- **판정**: 질문이 묻는 핵심을 다 맞히면 맞음, 일부만이면 부분, 핵심이 틀리면 틀림, 질문 전제가 지금 코드에 없으면 전제 변경(맞음·어긋남·볼 곳 대신 사라진 심볼·테스트만).
- **어긋남**: 사용자 답의 어느 문장이 틀렸는지 인용·지적하고, 빠진 요소는 "~에 대한 설명이 없음"으로.
  - 틀림이면 힌트만 - 왜 틀렸는지는 "어디를 다시 보면 모순이 보인다" 수준까지. 정답 문장을 쓰면 다시 찾을 이유가 사라진다.
- **문서 답 낡음**: 재도출 정답이 `**** 답`과 다를 때만. 판정과 무관하게 재도출 정답을 한두 문장으로 - 사용자가 `**** 답`을 펼쳐 대조할 때 낡은 답을 믿지 않게 한다.
- **볼 곳**: 부분이면 남은 간극의 근거(정답 문장은 `**** 답`에 있으므로 반복하지 않는다), 틀림이면 어긋남을 스스로 고칠 수 있게 하는 위치. 1~2개. 판정이 맞음이면 생략.
- 맞음이면 `어긋남`도 생략.
- heading 상태(`TODO`/`DONE`)는 건드리지 않는다.

### 4. 포매팅·보고

- §포매팅 실행.
- 채팅에는 질문별 판정 한 줄씩(문서 답 낡음이면 그 사실 덧붙임)과 파일 절대 경로만. 정답은 채팅에 반복하지 않는다(문서 `**** 답`에 있다). 틀림의 정답은 사용자가 요청할 때만 공개한다.

## org 표기

- **코드 위치는 [code-locations.md](../shared/code-locations.md)의 org 규칙을 따른다** - 어디에 쓰든 `[[file:/abs/path/foo.ts::42][foo.ts:42]]`, 같은 파일 반복도 전체 target, 링크는 verbatim 금지.
  - 예외: 반사실 질문의 힌트 1은 라인 없는 파일 링크(§5). 파일까지는 열린다.
  - 채팅 보고의 경로는 맨 경로(정본의 "그 밖" 규칙).
- **한 항목 = 한 bullet = 물리적으로 한 줄.** 문장 중간 하드 줄바꿈 금지(길어도 한 줄, 표시는 emacs soft-wrap).
- **식별자는 verbatim `=...=`로 감싼다**(예: =FLHitWindowRunner=). 안에 `=` 문자를 넣지 않는다(구문이 깨진다) - 대입식은 평문으로.
- **verbatim 뒤에 한글 조사를 붙이지 않는다.** `=Foo=에`는 org가 마크업으로 인식하지 못해 export에서 깨진다. 조사가 안 붙게 문장을 쓰고, 부득이하면 한 칸 띄운다.
- **헤딩 아래 본문은 별 개수 + 1칸 들여쓴다**(`*` → 2칸, `**` → 3칸).
- **다이어그램은 org mermaid 블록.**
  - `:file`은 `~/code-tour/<slug>-<kind>.png`, `:width "2048"`으로 폭 통일.
  - 렌더는 온디맨드 - 사용자가 `C-c C-c`/export로 PNG를 만든다(pre-render하지 않는다).

## 포매팅

먼저 [code-locations.md](../shared/code-locations.md)의 검사를 생성·수정한 .org 파일에 실행하고, 출력이 없을 때까지 위반을 고친다.

그다음 emacs로 org 들여쓰기를 정렬한다(emacs에서 열었다 저장한 것과 같은 상태). 여러 파일을 한 번에 넘길 수 있다. 이때 line ending도 실행 OS에 맞춘다(`set-buffer-file-coding-system` - Windows CRLF, 그 외 LF). emacs가 없거나 실패하면 파일은 그대로 두고 사용자에게 그 사실만 알린다.

```bash
emacs -Q --batch --eval '(progn (require (quote org)) (setq make-backup-files nil) (setq org-adapt-indentation t) (let ((dir default-directory)) (dolist (f command-line-args-left) (find-file (expand-file-name f dir)) (org-mode) (org-indent-region (point-min) (point-max)) (set-buffer-file-coding-system (if (memq system-type (quote (windows-nt ms-dos))) (quote utf-8-dos) (quote utf-8-unix))) (save-buffer))))' <생성·수정한 .org 파일들>
```
