# Code Tour

처음 보는 코드베이스를 **사용자가 직접 찾아 읽으며** 이해하도록 안내하는 문서를 만든다. 핵심은 확인 질문 - 사용자가 질문 heading 아래 답을 쓰고, 이 스킬로 검증받는 루프를 돈다.

## 경계

- `walkthrough`와 다르다. 그쪽은 이번 세션에서 만든 변경을 리뷰어에게 설명하고, 이쪽은 세션 컨텍스트 없이(콜드) 기존 코드를 학습한다.
- **정답을 먼저 주지 않는다.** 직접 찾아야 머리에 남는다. 문서에도, 검증 결과에도 정답을 쓰지 않는다 - 사용자가 명시적으로 요청할 때만 채팅으로 공개한다.
- 상태 전환(`TODO` → `DONE`)은 사용자 몫. 스킬은 heading을 `TODO`로 만들기만 하고 바꾸지 않는다.

## 모드 분기

- **선택 영역이 있으면 검증 모드.** 인자나 IDE 첨부 컨텍스트에 `<파일>:<시작>-<끝>` 형태의 선택이 있는 경우. → §검증 모드
- **없으면 생성 모드.** 인자는 범위로 해석. → §생성 모드

## 생성 모드

### 1. 범위와 언어 판정

- **범위**: 인자의 경로·주제. 생략 시 저장소 전체.
  - 부분 범위면 그 범위에 맞게 `전체 그림`을 줄이고 단계 수도 줄인다. 범위에 해당 없는 단계(예: UI가 없는 모듈의 UI 단계)는 빼되 순서는 유지.
- **독자 프로필**: [reader-profile.md](../shared/reader-profile.md)로 대상 언어·버전·프레임워크를 판정하고, 빠진 프로필은 물어 기록한 뒤 **낯선 영역**을 정한다. 대상 언어가 여러 개면 주력 하나를 대상으로, 나머지는 해당 단계에서만 언급.
- **낯선 영역을 문서에 싣는 위치**
  - 언어: 낯선 영역이 없으면(같은 언어, 독자 버전 이상) 언어 쪽 전제·포인트·대응표는 "해당 없음 - 주력 언어와 동일" 한 줄로. 버전 차이만 있으면 대응표 제목은 `<독자 버전> ↔ <대상 버전>`.
  - 프레임워크 낮음: `0단계 전제`에 그 프레임워크의 기반 절을 넣고, 각 단계 `언어·프레임워크 포인트`에서도 그 단계에 처음 나오는 프레임워크 기능을 설명한다.
  - 프레임워크 보통: 기반 절 없이 단계 포인트에서만.
  - 프레임워크 높음: 설명 생략. 관용과 다르게 쓴 곳만 `설계 포인트`로.

### 2. 탐색

- `CONTEXT.org`(다중 컨텍스트면 `CONTEXT-MAP.org` → 각 `CONTEXT.org`), `docs/adr/`, `docs/specs/`, 티켓 문서가 있으면 읽어 용어와 결정의 근거를 잡는다. **읽기만** 한다.
- 문서 위치는 [project-docs-storage.md](../shared/project-docs-storage.md)로 판정한다 - 외부 모드면 위 문서들은 `~/project-docs/<정규화된 저장소 절대경로>/` 아래 같은 상대 경로에 있다.
  - 외부 모드여도 저장소 안의 upstream 문서(`docs/adr/` 등)는 함께 읽는다. 두 곳 모두 있으면 둘 다 근거로 쓴다.
  - 인용은 실제로 읽은 쪽의 절대 경로로. 외부 문서는 저장소와 이력이 따로라 기준 커밋이 적용되지 않는다 - 라인과 함께 heading 이름을 적어 라인이 어긋나도 찾을 수 있게 한다.
- 프로젝트 `CLAUDE.md`의 규칙(테스트 정의 등)도 확인 질문 재료가 된다.
- 기준 커밋: `git rev-parse --short HEAD`. 라인 번호가 모두 이 커밋 기준이라는 사실을 `사용법`에 기록한다. 커밋되지 않은 변경이 범위 안에 있으면 그 사실도 함께 적는다.

### 3. 단계 구성

단계 순서는 고정 - 의존 방향을 따라 아래에서 위로 쌓아야 앞 단계 어휘로 다음 단계를 읽을 수 있다.

1. 어휘 - `CONTEXT`·ADR. 코드보다 먼저
2. 순수 모델 - 데이터 구조, 엔티티
3. 도메인 규칙 - 판정·계산 함수
4. 소유자/상태 - 상태를 들고 변경을 조율하는 객체
5. 경계 어댑터 - 직렬화, OS·네트워크·저장소 경계
6. UI
7. 테스트 - 설계가 실제로 고정된 곳

코드베이스에 따라 한 항목이 여러 단계로 나뉘어도 된다(예: 경계 어댑터 → 메시지 DTO + 링크). 해당 없는 항목은 뺀다.

### 4. 단계 내용

각 단계 = `먼저 읽을 것` → `코드` → `설계 포인트` → `언어·프레임워크 포인트` → `확인 질문`. 해당 없는 하위 섹션은 생략(확인 질문은 생략 불가).

- **먼저 읽을 것**: 이 단계 전에 읽을 ADR·spec·CONTEXT 절. 절대 경로로.
- **코드**: 읽을 순서대로 번호 매긴 `절대경로:라인 =심볼= - <왜 여기>`. 선언부 → 진입 함수 → 핵심 함수 순.
- **설계 포인트**: 코드에 박힌 결정과 그 이유. 주석·ADR에 근거가 있는 것만. `*굵게*` 한 구절 + 설명.
- **언어·프레임워크 포인트**: 언어는 주력 언어(버전 포함)에 **직접 대응이 없거나 의미가 다른 것만** - 주력 언어에도 똑같이 있는 문법은 소음이다. 각 항목에 주력 언어의 가장 가까운 개념을 `≈` 로 붙인다. 프레임워크는 §1 숙련도별 분량을 따른다. 모든 항목에 이 코드의 실제 등장 위치 하나를 단다.
- **확인 질문**: §5

### 5. 확인 질문

질문이 이 문서의 핵심 산출물. 사용자가 그 heading 아래 답을 쓰고 검증 모드로 확인받는다 - 그래서 bullet이 아니라 heading이어야 한다.

- 형식: `** TODO 확인 질문` 아래 질문마다 `*** <질문>` heading.
- heading 하나에 물음 하나, 한 문장. "A는 무엇이고, B는 어디이며, 왜 C인가"처럼 묶으면 heading이 문단이 되고 검증 판정도 흐려진다 - 나눠서 별도 질문으로.
- 단계당 2~3개. 아래 세 종류 중 **최소 2종**을 섞는다 - 한 종류만이면 같은 근육만 쓴다.
  - 이유: "왜 X는 Y가 아니라 Z인가"
  - 반사실: "X를 없애거나 바꾸면 무엇이 깨지나"
  - 추적: "A가 일어나면 B까지 어떤 경로로, 무엇이 실려 가나"
- **확정 가능한 것만.** 코드·주석·테스트·ADR로 답이 하나로 정해져야 검증할 수 있다. 의견·취향을 묻지 않는다.
- **최소 두 곳을 이어야 답이 나오는 것.** 한 줄 주석을 그대로 옮기면 끝나는 질문은 찾기 연습이지 이해 확인이 아니다.
- **정답은 기록하지 않는다.** 출제 시점에 정답을 스스로 확정해 두되(확정 못 하면 그 질문은 버린다) 문서에는 쓰지 않는다.
- 일부 질문에만 단서 한 줄: `- 단서: /abs/path:line`. 반사실 질문의 단서는 깨질 테스트 파일. 모든 질문에 달면 찾는 과정이 사라진다.

```org
** TODO 확인 질문

*** 워치가 같은 완료를 두 번 보냈을 때 두 번째 ack에는 무엇이 실리는가

*** =publish= 에서 종료 정보를 이어 싣지 않으면 어떤 테스트가 깨지나

    - 단서: /abs/path/Tests/HealthRecordingIntegrationTests.swift:88
```

### 6. 문서 작성

`~/code-tour/YYYY-MM-DD-HHMM-<slug>.org`에 쓴다(`<slug>` = 저장소명 또는 범위 kebab). 디렉터리가 없으면 만든다. 문서가 저장소 밖에 있으므로 ADR·spec·ticket·CONTEXT 인용도 전부 절대 경로.

골격은 고정. 단계 heading은 전부 `TODO`.

```org
#+title: <저장소> 코드 따라 읽기 - <범위> (<주력 언어> 프로그래머용)

<이 문서가 설계 문서를 대신하지 않는다는 한 줄 - 이유는 ADR에, 여기는 그 결정이 코드 어디에 있는지>

* TODO 사용법

  - 단계를 순서대로 진행. 각 단계는 "먼저 읽을 것 → 코드 → 설계 포인트 → 언어·프레임워크 포인트 → 확인 질문"
  - 경로는 절대 경로 + 라인 번호 - emacs =M-x ffap= 로 점프
  - 라인 번호는 커밋 =<sha>= 기준. 어긋나면 함께 적힌 심볼 이름으로 검색
  - 확인 질문 heading 아래 답을 쓰고, 그 영역을 선택해 =/code-tour= 로 검증
  - 막히면 해당 영역의 단위 테스트 - 테스트 이름이 곧 규칙 목록

* TODO 전체 그림 먼저

** 한 문장 요약

   <시스템의 정체 한 문장>

** 계층도

   #+begin_src mermaid :file ~/code-tour/<slug>-layers.png :width "2048"
   <계층·의존 방향 flowchart>
   #+end_src

   - <계층도를 읽는 법 1~2줄>

** 디렉터리와 타깃

   - =/abs/path/dir/= - <역할>

* TODO 0단계: 읽기 전 전제 - <대상 언어>, <숙련도 낮은 프레임워크>

** TODO 0-1. <전제>

   - <설명 - 주력 언어와의 차이 중심>

** TODO 0-N. <프레임워크> 기반: <주제>    ← 숙련도 낮음인 프레임워크만

   - <설명 - 매크로가 생성하는 것, 수명, 실행 모델 등>

* TODO 1단계: <제목>

** TODO 먼저 읽을 것

** TODO 코드

** TODO 설계 포인트

** TODO 언어·프레임워크 포인트

** TODO 확인 질문

*** <질문>

* 시나리오로 따라가기

** 시나리오 A: <가장 중요한 흐름>

   #+begin_src mermaid :file ~/code-tour/<slug>-scenario-a.png :width "2048"
   <sequenceDiagram>
   #+end_src

   1. <단계> → /abs/path:line =심볼=
   N. 이 흐름을 고정한 테스트: /abs/path:line

* <주력> ↔ <대상> 대응 요약

  | <대상>  | <주력>에 가장 가까운 것 | 주의 |
  |---------+-------------------------+------|

* 다음에 해볼 것

  - <코드를 일부러 바꿔 어떤 테스트가 깨지는지 보는 실험 등>
```

- `0단계 전제`: 언어는 모르면 코드 곳곳이 소음으로 보이는 것 3~6개. 숙련도 낮음인 프레임워크마다 기반 절 2~5개. 각 단계의 `언어·프레임워크 포인트`에서 반복하지 않는다.
- 시나리오: 단계를 가로지르는 핵심 흐름 1~4개. 각 화살표가 실제 호출이어야 한다.
- 대응표: 문서에 등장한 언어 포인트의 요약(프레임워크 항목은 주력 언어 쪽 대응이 있을 때만). 새 항목을 여기서 처음 소개하지 않는다.

### 7. 포매팅·보고

- §포매팅 실행.
- 채팅에는 문서 전문 대신 아래만: 범위, 단계 수, 질문 수, 기준 커밋, 생성한 org 파일의 **절대 경로**.

## 검증 모드

### 1. 대상 추출

- 선택 영역 안의 `*** <질문>` heading만 대상. 영역 밖 질문은 건드리지 않는다.
- 답 = 질문 heading 아래 본문에서 `- 단서:` 줄과 기존 `**** 검토` 서브트리를 뺀 것.
- 답이 비어 있으면 검토를 쓰지 않고 "답 없음"으로 보고만 한다.

### 2. 정답 재도출

- 문서에 정답이 없으므로 **지금 코드에서** 다시 도출한다. 질문·단서·답이 가리키는 위치를 실제로 열어 확인한다 - 답이 그럴듯해 보인다는 이유로 판정하지 않는다.
- `사용법`의 기준 커밋과 `git rev-parse --short HEAD`가 다르면 검토에 그 사실을 적는다(라인·동작이 바뀌었을 수 있다).

### 3. 검토 작성

질문 heading 바로 아래 서브트리 끝에 `**** 검토`를 쓴다. 이미 있으면 덮어쓴다(이전 검토는 지운다).

```org
**** 검토

     - 판정: 맞음 | 부분 | 틀림
     - 맞음: <맞은 부분>
     - 어긋남: <틀린 문장 지적, 정답은 쓰지 않음>
     - 볼 곳: /abs/path:line
     - 기준: 문서 =<sha>= / HEAD =<sha>=   ← 다를 때만
```

- **판정**: 질문이 묻는 핵심을 다 맞히면 맞음, 일부만이면 부분, 핵심이 틀리면 틀림.
- **어긋남**: 사용자 답의 어느 문장이 틀렸는지 인용·지적하고, 왜 틀렸는지는 "어디를 다시 보면 모순이 보인다" 수준까지만. 정답 문장을 쓰면 다시 찾을 이유가 사라진다. 빠진 요소는 "~에 대한 설명이 없음"으로.
- **볼 곳**: 어긋남을 스스로 고칠 수 있게 하는 위치 1~2개. 판정이 맞음이면 생략.
- 맞음이면 `어긋남`도 생략.
- heading 상태(`TODO`/`DONE`)는 건드리지 않는다.

### 4. 포매팅·보고

- §포매팅 실행.
- 채팅에는 질문별 판정 한 줄씩과 파일 절대 경로만. 정답은 사용자가 요청할 때만 공개한다.

## org 표기

- **코드 위치는 어디에 쓰든 `/abs/path/foo.ts:42`**(절대 경로 + 단일 라인). emacs `ffap`/compilation-mode 점프용.
  - 금지: 상대경로(`foo.ts:42`), 라인 범위(`:42-50`), verbatim으로 감싸기(점프가 막힌다).
  - 산문에 인라인해도 된다 - 형식만 맞으면 문장 중간에서도 점프된다.
- **한 항목 = 한 bullet = 물리적으로 한 줄.** 문장 중간 하드 줄바꿈 금지(길어도 한 줄, 표시는 emacs soft-wrap).
- **식별자는 verbatim `=...=`로 감싼다**(예: =FLHitWindowRunner=). 안에 `=` 문자를 넣지 않는다(구문이 깨진다) - 대입식은 평문으로.
- **verbatim 뒤에 한글 조사를 붙이지 않는다.** `=Foo=에`는 org가 마크업으로 인식하지 못해 export에서 깨진다. 조사가 안 붙게 문장을 쓰고, 부득이하면 한 칸 띄운다.
- **헤딩 아래 본문은 별 개수 + 1칸 들여쓴다**(`*` → 2칸, `**` → 3칸).
- **다이어그램은 org mermaid 블록.**
  - `:file`은 `~/code-tour/<slug>-<kind>.png`, `:width "2048"`으로 폭 통일.
  - 렌더는 온디맨드 - 사용자가 `C-c C-c`/export로 PNG를 만든다(pre-render하지 않는다).

## 포매팅

쓴 뒤 emacs로 org 들여쓰기를 정렬한다(emacs에서 열었다 저장한 것과 같은 상태). 여러 파일을 한 번에 넘길 수 있다. 이때 line ending도 실행 OS에 맞춘다(`set-buffer-file-coding-system` - Windows CRLF, 그 외 LF). emacs가 없거나 실패하면 파일은 그대로 두고 사용자에게 그 사실만 알린다.

```bash
emacs -Q --batch --eval '(progn (require (quote org)) (setq org-adapt-indentation t) (let ((dir default-directory)) (dolist (f command-line-args-left) (find-file (expand-file-name f dir)) (org-mode) (org-indent-region (point-min) (point-max)) (set-buffer-file-coding-system (if (memq system-type (quote (windows-nt ms-dos))) (quote utf-8-dos) (quote utf-8-unix))) (save-buffer))))' <생성·수정한 .org 파일들>
```
