# Deepening

의존성을 고려해 얕은 모듈들의 클러스터를 안전하게 깊게 만드는(deepen) 방법. [SKILL.md](SKILL.md)의 어휘를 전제한다: **모듈(module)**, **인터페이스(interface)**, **심(seam)**, **어댑터(adapter)**.

## 의존성 분류(Dependency categories)

깊게 만들 후보를 평가할 때, 그 의존성을 분류한다. 분류에 따라 깊게 만든 모듈을 심을 가로질러 어떻게 테스트할지가 정해진다.

### 1. 인프로세스(In-process)

순수 계산, in-memory 상태, I/O 없음. 항상 깊게 만들 수 있음: 모듈들을 병합하고 새 인터페이스를 통해 직접 테스트한다. 어댑터 불필요.

### 2. 로컬 대체 가능(Local-substitutable)

로컬 테스트 대역(stand-in)이 있는 의존성(Postgres에 대한 PGLite, in-memory 파일시스템). 대역이 존재하면 깊게 만들 수 있음. 깊게 만든 모듈은 테스트 스위트에서 돌아가는 대역과 함께 테스트한다. 심은 내부에 있고, 모듈의 외부 인터페이스에는 포트(port)가 없다.

### 3. 원격이지만 소유(Remote but owned — Ports & Adapters)

네트워크 경계 너머에 있는 당신 자신의 서비스(마이크로서비스, 내부 API). 심에 **포트(port)**(인터페이스)를 정의한다. 깊은 모듈이 로직을 소유하고, 전송(transport)은 **어댑터(adapter)**로 주입된다. 테스트는 in-memory 어댑터를, 프로덕션은 HTTP/gRPC/queue 어댑터를 쓴다.

권장 형태: *"심에 포트를 정의하고, 프로덕션용 HTTP 어댑터와 테스트용 in-memory 어댑터를 구현한다. 그러면 네트워크 너머로 배포되더라도 로직은 하나의 깊은 모듈에 앉는다."*

### 4. 진짜 외부(True external — Mock)

당신이 제어하지 못하는 서드파티 서비스(Stripe, Twilio 등). 깊게 만든 모듈은 외부 의존성을 주입된 포트로 받는다. 테스트는 mock 어댑터를 제공한다.

## 심 규율(Seam discipline)

- **어댑터가 하나면 가상의 심, 둘이면 진짜 심이다.** 최소 두 개의 어댑터(보통 프로덕션 + 테스트)가 정당화되지 않으면 포트를 도입하지 마라. 어댑터 하나짜리 심은 그저 간접 참조(indirection)일 뿐이다.
- **내부 심 vs 외부 심.** 깊은 모듈은 인터페이스의 외부 심뿐 아니라 내부 심(구현에 private하며 자체 테스트가 사용)도 가질 수 있다. 테스트가 쓴다는 이유만으로 내부 심을 인터페이스로 노출하지 마라.

## 테스트 전략: 겹치지 말고 교체하라(replace, don't layer)

- 얕은 모듈에 걸린 옛 유닛 테스트는 깊게 만든 모듈의 인터페이스에서의 테스트가 생기면 쓰레기가 된다. 삭제하라.
- 깊게 만든 모듈의 인터페이스에서 새 테스트를 작성하라. **인터페이스가 곧 테스트 표면이다.**
- 테스트는 내부 상태가 아니라 인터페이스를 통해 관찰 가능한 결과(observable outcome)를 단언(assert)한다.
- 테스트는 내부 리팩터를 견뎌내야 한다 — 구현이 아니라 동작을 서술하기 때문이다. 구현이 바뀔 때 테스트를 바꿔야 한다면, 그 테스트는 인터페이스 너머를 테스트하고 있는 것이다.
