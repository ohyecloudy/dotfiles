# Design It Twice

선택한 깊게 만들(deepening) 후보에 대해 대안 인터페이스를 탐색하고 싶을 때, 이 병렬 서브 에이전트 패턴을 쓴다. "Design It Twice"(Ousterhout)에 기반한다: 당신의 첫 아이디어가 최선일 가능성은 낮다.

[SKILL.md](SKILL.md)의 어휘를 쓴다: **모듈(module)**, **인터페이스(interface)**, **심(seam)**, **어댑터(adapter)**, **레버리지(leverage)**.

## 프로세스

### 1. 문제 공간을 규정한다(Frame the problem space)

서브 에이전트를 띄우기 전에, 선택한 후보에 대해 문제 공간을 사용자용으로 설명하는 글을 쓴다:

- 새 인터페이스라면 만족시켜야 할 제약(constraint)
- 그것이 의존할 의존성, 그리고 각각이 어느 분류에 속하는지([DEEPENING.md](DEEPENING.md) 참고)
- 제약을 구체화할 대략적 예시 코드 스케치 — 제안이 아니라 제약을 손에 잡히게 만드는 수단일 뿐

이걸 사용자에게 보여준 뒤, 곧바로 2단계로 넘어간다. 서브 에이전트가 병렬로 일하는 동안 사용자는 읽고 생각한다.

### 2. 서브 에이전트를 띄운다(Spawn sub-agents)

3개 이상의 서브 에이전트를 병렬로 띄운다. 각각은 깊게 만든 모듈에 대해 **근본적으로 다른(radically different)** 인터페이스를 내놓아야 한다.

각 서브 에이전트에게 별도의 기술 브리프(파일 경로, 결합 세부사항, [DEEPENING.md](DEEPENING.md)의 의존성 분류, 심 뒤에 무엇이 앉는지)로 프롬프트한다. 이 브리프는 1단계의 사용자용 문제 공간 설명과 독립적이다. 각 에이전트에게 서로 다른 설계 제약을 준다:

- Agent 1: "인터페이스를 최소화하라: 진입점 1~3개를 목표로. 진입점당 레버리지를 최대화하라."
- Agent 2: "유연성을 최대화하라: 많은 유스케이스와 확장을 지원하라."
- Agent 3: "가장 흔한 호출자에 최적화하라: 기본 케이스를 사소하게(trivial) 만들어라."
- Agent 4(해당 시): "심을 가로지르는 의존성을 위해 ports & adapters로 설계하라."

각 서브 에이전트가 아키텍처 언어와 프로젝트 도메인 언어에 일관되게 이름을 붙이도록, 브리프에 [SKILL.md](SKILL.md) 어휘와 CONTEXT.md 어휘를 모두 포함한다.

각 서브 에이전트의 출력:

1. 인터페이스(타입, 메서드, 파라미터에 더해 불변식, 순서, 에러 모드)
2. 호출자가 어떻게 쓰는지 보여주는 사용 예시
3. 구현이 심 뒤에 무엇을 숨기는지
4. 의존성 전략과 어댑터([DEEPENING.md](DEEPENING.md) 참고)
5. 트레이드오프: 레버리지가 높은 곳과 얇은 곳

### 3. 제시하고 비교한다(Present and compare)

사용자가 하나씩 흡수할 수 있게 설계를 순차적으로 제시한 뒤, 산문으로 비교한다. **깊이**(인터페이스에서의 레버리지), **지역성**(변경이 모이는 곳), **심 배치(seam placement)**로 대조한다.

비교 후, 당신 자신의 권고를 낸다: 어느 설계가 가장 강하다고 보는지와 그 이유. 서로 다른 설계의 요소들을 잘 조합할 수 있으면 하이브리드를 제안한다. 의견을 분명히 하라 — 사용자는 메뉴가 아니라 강한 판단을 원한다.
